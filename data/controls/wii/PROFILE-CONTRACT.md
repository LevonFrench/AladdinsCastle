# Shell and stick profiles

Canonical source: `data/controls/wii/shell-and-stick.toml`, version `shell-stick/1`.
The authoring compiler is `tools/wii_shell_stick.py`. The stable callable entry
point is `tools/wii_controls.py:render_profile(route, mode, primary_hand)`.
It returns UTF-8 bytes; it performs no install or input operations.

`data/controls/wii/generated/<route>/<mode>-<hand>.ini` is the exact generated
`Config/WiimoteNew.ini` payload. Routes are `dolphinxr` and `flat-dolphin`;
modes are `split`, `docked`, `two-remotes`; hands are `right` and `left`.
`generated-files.json` identifies every payload by SHA256. Install recipes and
sitting preparation copy those bytes unchanged. Changing hold or handedness
selects another generated payload; it never applies a second mapping layer.

Native device and input spellings are checked against the shipped OpenXR
controller profile and pinned source. Modifier chords explicitly suppress
unmodified actions. Both thumbstick clicks reserve recenter and suppress game
button/fallback expressions. Lead owns the separate hotkey settings and
initial facing logic. Physical acceleration/gyro and simulated button motion
are both represented; gameplay recognition remains an owner-run check.

The bridge uses `generated/flat-dolphin/<mode>-<hand>.json`: logical action,
physical hand, boolean token expression and DSU wire control. Evaluate logical
bindings before encoding; suppress all game button/fallback outputs for the
reserved recenter chord. IR occupies the DSU right stick and attachment analog
input the left stick. Home uses the dedicated DSU PS byte, not a button-mask bit.
Lead owns transport consumption, analog thresholds and native held-model drawing.

Check generated bytes with `python tools/wii_shell_stick.py`; rebuild with
`--write`. Tests use synthetic inputs and do not establish emulator/headset
acceptance. Game option layouts/actions are separate per-game question data.
