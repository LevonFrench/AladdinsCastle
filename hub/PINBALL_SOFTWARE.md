# Pinball software boundary

For the ordinary user flow, see [Playing Pinball from Hub](PINBALL.md).

The tab scans one explicitly selected folder in place. It never recurses into subfolders, follows linked child entries, copies tables, extracts assets, downloads media or reads download addresses into its table model. An optional local VPS JSON file, ROM folder and media folder are selected separately. Exact same-stem raster wheels and `.directb2s` files are associated locally; absent art uses a title tile.

The independently implemented CFB reader supports regular FAT and mini-FAT streams, with bounds, cycles, directory identities and metadata budgets checked. Reads are limited to table information and `GameStg/GameData`; geometry/textures/sounds are not extracted. Metadata streams are capped at 8 MiB, script text at 2 MiB and total reads per table at 32 MiB. Protected or unsupported script records remain unclassified, with an explicit error. Table names, paths and inventory receipts stay in the user's data, not the catalog.

VR evidence is conservative: a unique VPS machine match requires title, maker and year, followed by a unique VPX author/version match whose features include `VR`. When no machine has the table's name, the Hub asks a distance matcher ported from VPin Studio (through Visual Pinball Infinite): the file name's name, maker and year, then the table info's name, then the ROM its script names. Its find is taken only when no other machine is as near, the maker and year the file gives agree, and, unless the ROM found it, every word and number of the machine's name is in the table's with no number or edition word (LE, Pro) left over. The row's `vpsFound` says how the machine was found. A VPS file's features also count when the matcher's nearest file has every one of the table's authors and its version, with spaces and dots aside (`ClarkKent`, `1.1.3` and `1.13`); `vpsFileFound` says which way. Games VPS lists no VPX table for are left to the exact rules. A script match requires an actual room-switch assignment plus VR object visibility references; conditions, comments and string messages cannot supply that assignment. Menu-based room options and inline assignments are recognized. This proves script evidence, not that a room is enabled or visually correct. Missing/ambiguous evidence is left out unless explicitly marked by the user; exclusions, favourites and filters are Hub-owned settings.

ROM readiness means a single static ROM reference has a same-named local ZIP, not that its bytes have been audited or the table has run. Dynamic, conflicting and unsupported references stay unknown. `needs no ROM` is a script-metadata inference; executable behavior remains unaccepted. Neither a ROM ZIP nor a backglass is opened by inventory association.

A table's page shows the high scores and mode champions PinMAME saved in its `.nv` file, read fresh each time the table is opened and after each game, and never kept in the scan. The file is found in VPinMAME's own `nvram_directory` setting, else the VPinMAME folder's `nvram`, else an `nvram` folder beside the ROM folder. For a table with several possible ROM sets, the newest saved file counts. The file is only read, up to 1 MB. Where each score sits is taken from the [Pinball Memory Maps](https://github.com/tomlogic/pinball-memory-maps) project: `tools/pinball_score_maps.py` keeps just the score entries of a pinned commit in `data/pinball-score-maps.json` (ODbL), which is built into the Hub. A set the maps do not cover says so. The scores are what the machine itself shows, including its factory defaults until they are beaten. Scores that a table's own script saves (`VPReg.stg`) are not read yet. `hubtool pinball-scores <nvram-folder> <set>...` prints the same result.

`hubtool scan-pinball <tables> [<database> [<roms> [<media>]]]` returns the private inventory. `hubtool plan-pinball <table> <exe> <unused-session> <vr|desktop>` prints a diagnostic without creating settings or starting anything. R4 authorizes ordinary VPX persistence. A desktop plan uses only `-Play <absolute-table>`, with the executable directory as its working directory. A `vr` plan with an owned root adds `-TableIni <owned-root>/user/pinball/<table id>.ini`: VPX loads that file as the table's settings layer above the application settings (`TableBasedCommand::LoadTable` and `PinTable::SetSettingsFileName` at the audited tag), and `Player` reads `[PlayerVR] AskToTurnOn` through that layer, so `0` there forces VR without editing the user's settings. Printing a plan creates nothing. At launch Hub writes only that owned file: a first-time copy of the table's own `.ini` beside the table (read, never written) with the one key set, later only the key. VPX keeps its configured ROM, plugin and other settings; table-level changes made in VPX are saved to the owned file. The Hub never copies, edits or redirects the owner's library.

The detail's Play button uses the shared launch service. A changed or unreadable scanned table requires a rescan; a missing known ROM or excluded table is refused. The now-playing card retains the exact table/executable independently of later navigation. Recent-play metadata belongs to Hub settings. Hub asks for VR explicitly by default (the `pinballHeadset` setting; off leaves the choice to VPX and passes no settings file), and does not start SteamVR or change the OpenXR runtime for this route. With VR forced and no headset reachable, VPX shows its own retry dialog on the desktop. The last scan is kept in `user/cache/pinball-scan.json` and shown when the tab opens for the same folders; a table's identity, size and time are still rechecked at launch.

The controls card consumes the Guns lane's `vpx-openxr` route through `resolveRoute` and the existing universal view. Its exit warning is retained (no hold-to-quit in a table; leave from the Hub panel's Exit game); planned/unavailable execution labels do not imply a running bridge. The shared now-playing card preserves the current tab and exact route. Global Stop cancels preparation or requests the same normal Windows child-window close as Exit, retaining close intent through child startup without a force timer. Restart runs only after successful process completion; Stop cancels a pending restart. Recentre stays disabled. Linux clean close and actual score-saving behavior are unaccepted.

The detail and diagnostic plan explain that VPX uses its normal settings and saves scores. [The earlier isolation audit](VPX_ISOLATION.md) remains historical source evidence; its all-output-confinement requirement was superseded by R4. Real VPX launch in a headset, clean exit and score saving still require a runtime check with a headset.

Wii disc identity is a separate bounded metadata check. WBFS host-sector size is derived from validated shifts and a single-disc slot; the copied header and Wii magic are checked. Rescans bypass metadata-only cache admission for ISO/GCM/WBFS, and admitted disc IDs are reread again immediately before child spawn. [Upstream WBFS layout reference](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/DiscIO/WbfsBlob.cpp). `hubtool identify-disc <file>` exposes the same read-only reader without inspecting game payloads or starting an emulator.
