# Release 0.01 checklist

Release guidance refreshed 2026-11-07 against source `ee31a252d9d771b1edf3c96f7d34f9f09929d036`. This page says what is proven without the owner's PC, what still
needs a second PC and a headset, and which owner decisions block 0.01. It is a
checklist, not a release note: there is no published 0.01 release yet. Evidence levels (E1, E2,
E3) are explained in [docs/status/current.md](../status/current.md). Only the owner's
own headset verdict is E3.

## Candidate identity and evidence

Keep these identities separate: the source revision, a CI artifact, a development
installation, and the candidate handed to a tester. The current Hub workflow
uploads `AladdinsCastle-Windows-x64`, containing `AladdinsCastle.zip`.
`BUILD-INFO.txt` records the source commit. Packaging checks a clean source tree,
matching product identity and a build receipt hashing the four shipping EXEs;
this ties staging to the build inputs, not to headset acceptance.

At this checkpoint draft PR #177 is unmerged. Local regression receipts for its
initial code candidate (subsequently committed as `75c3b4d0`) record 381 passing native Qt cases, zero failures and one existing
opt-in archive preflight skip. Those receipts cover synthetic installer,
launch/process and Hub integration checks; they do not certify main, a live
installation, an emulator or a headset. The producer must retain the exact tested
revision and new CI results for the final combined release candidate.

For each tester handoff, record the workflow/run URL, source commit, package SHA-256,
separate system-build identity and dependencies, first game/view, and the results
of the gates below. Never substitute an earlier green run for the candidate's run.

## What the CI fresh-install check covers (no headset)

The `fresh-install` job in `.github/workflows/ci.yml` takes the portable Windows Hub
ZIP that the `hub` job builds and exercises a synthetic first-run path on a Windows runner. The script is
`hub/packaging/tests/Test-FreshInstall.ps1` (Windows PowerShell 5.1). It keeps a
summary, the pictures and the Hub's own files as the CI artifact `fresh-install-evidence`.

| Step | What is checked |
|---|---|
| Install | The ZIP unpacks into an empty folder as one package folder. The required runtime payload and privacy rules pass the same gate used by staging, run on the unpacked copy. This is not exhaustive runtime dependency or privacy certification. The ZIP ships no offscreen Qt plugin. |
| First run | The packaged Hub starts with no game folders and no settings, on a bare PATH and a throwaway user profile, so it must use its own DLLs. It counts its catalog, opens the first-run Set-up page, takes a picture of its own window, quits by itself, and starts no game. Set-up is not marked done. |
| Set-up, empty | A folder with nothing in it: nothing is called ready, and the games it knows are listed as not found with the name the Hub looks for. |
| Set-up, error | Folders and programs that do not exist: nothing is called ready; a missing program is reported "not right" with a reason in words. |
| Set-up, unrecognised | A folder of fake files (zero-filled bytes and a text file with game-style names, never a game): the fake disc and the fake archive are named as not recognised, with a reason, and the folders are not changed. |
| Uninstall | The install folder deletes cleanly, no Hub process is left, and nothing is left in the profile, temp folder or registry it ran under or in the machine's real profile and registry under the product's name. |

The first run of this check found a real leftover: Qt stored compiled copies of the Hub's
screens in the user's AppData, outside the install folder, so deleting the folder did not
remove everything. The Hub now keeps that cache in its own `user/cache/qmlcache` folder.
The check also uses a diagnostic switch, `AC_UI_LIBRARY_SCAN`, which reads the game library
and then the Set-up folders (as the buttons do) and takes the picture once that has finished.

For this test only, the Qt offscreen plugin from the build Qt is copied in after the
package has been checked. The package a tester gets does not contain it.

Also proven in CI before this (not repeated here): the catalog and install-engine
tests, the Hub's own Qt tests, the portable package payload check, that the emulator
patches still apply to their pinned commits, and that `acvr-ps1.exe` compiles.

### What CI still does not prove

- That any game starts or looks right. The fake files are not games.
- That the Hub works on a PC with a real graphics card, a real display or a headset
  (CI draws with the software renderer into a hidden window).
- That SteamVR registration, the SteamVR dashboard panel or the Quest connection work.
- That any emulator or VR host (Supermodel, MAME, PCSX2, Dolphin, Flycast, `acvr-ps1`)
  runs. The main workflow compiles `acvr-ps1`; separate workflows compile patched
  emulators. They do not run games. The VPX compile workflow uploads
  `vpx-acvr-10.8.1.5436-hold-to-quit` (EXE, README and SHA-256), not a complete
  tested VPX installation. These outputs are separate from the Hub ZIP.
- That Windows Defender or SmartScreen accept the unsigned package.

## Owner decisions blocking 0.01

From the last section of `DECISIONS.md`, "Open questions waiting for the owner", and the
2026-10-22 note on the new repository.

1. **Which path is 0.01?** One hero game (the reviewers suggest Sega Rally 2 DX on Model
   3, fallback Mario Kart 64) built by the owner and handed over as a binary pack, or "run
   the Hub and bring your own emulator builds". The fresh-install job covers synthetic Hub setup for either path; it does not choose one.
2. **Which E2-only features are hidden or marked experimental in the 0.01 Hub?** The
   selection must follow the dated per-view evidence, including unresolved PS2 and
   pinball headset checks. Offline fixes do not automatically remove an experimental label.
3. **New git repository.** At 0.01 the project moves to a new repository (the current
   history carries the old name). Nothing is created or migrated until you say 0.01 is
   happening.
4. **Allowed to hand out binaries?** A binary pack for the hero game means shipping the
   built emulator. Licences and the notices file need a look first (see
   [docs/legal.md](../legal.md)); this is not yet in `DECISIONS.md` and is the
   owner's call.

The other open questions in `DECISIONS.md` (separate GitHub identity for agents, whether
interactive work preempts overnight lanes on the heavy-run lease, a budget before runs
over two hours, retiring the old worktrees) do not block the release.

Gun version/design selection remains deferred. Existing geometry tests, pictures
and compile results do not constitute gun acceptance; do not promote a version
through this checklist.

## Before saying "0.01"

- [ ] Identify the exact candidate: source commit, workflow/run, Hub ZIP SHA-256,
      separate system build/dependencies and first game/view. Confirm the extracted
      `BUILD-INFO.txt` agrees with the handoff.
- [ ] `fresh-install` and the rest of CI are green on that candidate;
      retain the summary/receipts. Mark compile-only and synthetic results as such.
- [ ] The complete runtime bundle is available for the chosen route, including
      needed launcher/interpreter, core, profiles and DLLs. No development folders
      or implicit machine-wide tool paths are required.
- [ ] The owner picks the tester path (decision 1) and the hidden features (decision 2).
- [ ] The package is installed on a second clean PC, by following only
      [the tester walkthrough](../TESTER-QUICKSTART.md), and the first game starts. Record Windows/display and system-build details,
      Set-up, launch, quit and restart; keep private paths out of public reports.
- [ ] The selected headset checks are done: picture, aim/controls, Start/Select,
      recentre, quit/return, comfort and pacing. Record the owner verdict for the
      exact game/view/build and preserve failures or untested steps.
- [ ] The new repository exists (decision 3) and the privacy check is clean there.
