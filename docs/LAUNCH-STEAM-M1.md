# M1 launch and Steam library implementation

Lane G uses `ac::launch::flatRequest` to choose a flat catalog variant with verified media and a located emulator. It accepts the scanner's complete JSON result or the install engine's keyed bindings. Scanner size/mtime fingerprints for media, support archives and emulators are checked before launch. Missing or changed media are refused without hashing large disc images. Stale unrelated emulators do not block the selected route. A legacy default VR recipe cannot override the available flat route. The catalog exposes `preferredVariantId`; a generated flat variant with all requirements verified becomes Ready without an install recipe ownership manifest. Authored variants retain the three install verification gates. The install engine prepares the isolated emulator profile on a worker; no original emulator configuration is read.

`LaunchService` starts an asynchronous `QProcess`, keeps a per-game process lock, exposes `playing`, and emits `started`, `finished`, `runtimeStateReady` and `raiseHubRequested`. Supply a current runtime snapshot with `setRuntimeStateSource` so launch updates preserve scan/install state. The card/detail model receives a `playing` role and the label Playing without changing existing state enum numbers. Exit records last-played in Hub user storage and reports the final 40 log lines on nonzero exit. The CLI `aladdinscastle-hub --launch <game-id>` uses the same preflight and process path. Optional `--install-root`, `--bindings` and `--variant` select an isolated user root, scanner receipt and flat route.

Flat launches use `runtime = none` and never start SteamVR. A SteamVR request looks up the public Steam location and library folders, starts the native `vrmonitor` launcher only if needed, and polls for `vrserver` for at most 60 seconds. `XR_RUNTIME_JSON` is set only in the child environment. No global runtime value is written. Runtime detection accepts injected environment/registry inputs for tests and follows environment, Windows registry, then Linux XDG search order. Empty inherited overrides remain explicit overrides.

## Steam review and write API

`ac::steam::preview(WriteRequest)` returns the target, backup folder, art paths, account, shortcut fields and before/after hashes. An explicit numeric userdata account is required. The account discovery function lists config directory names only; it does not read login/account databases. `apply(request, approvedPreview, ownerApproved)` requires approval, checks Steam and its web helpers are closed, takes a Hub lock, rejects a stale preview, creates backups, and atomically writes the VDF. It retains the last ten backups per replaced file. An art failure is reported separately after the library write.

Binary VDF nodes retain their original bytes, order, duplicate unknown keys and end markers. Unowned entries are copied byte for byte even when owned entries change. Unknown *fields* using known types survive; unsupported type encodings and malformed/truncated input fail closed. Parsing is bounded to 16 MiB, 100,000 nodes and 32 levels. Ownership requires both `AladdinsCastle` and `AladdinsCastle:<game-id>` tags. Colliding AppIds belonging to another entry are refused. The existing owned AppId persists when its title or executable changes. Flat entries set `OpenVR = 0`.

Four PNG names use the unsigned 32-bit AppId: `<appid>.png`, `<appid>p.png`, `<appid>_hero.png`, `<appid>_logo.png`. The local art provider supplies images; the fallback uses generated title/manufacturer art. Logos retain transparency. Grid art ownership is recorded by hash in Hub storage. Edited or unowned art is preserved unless a fresh preview explicitly requests `overwriteCustomArt`. Removal operates only after locating the matching owned entry and backs up unchanged owned art; custom art is retained. Art ownership receipt hashes and per-file actions are part of the approval preview. No Steam files are written automatically from install/uninstall; integration must present this preview and obtain the owner's approval before applying it.

`steamtool preview <request.json>` prints the exact preview without writes. `steamtool apply <request.json> <approved-preview.json> --owner-approved` applies only that unchanged preview with Steam closed. The explicit approval flag must only be used after the owner approves the concrete preview. It never starts or closes Steam. Request files are private local receipts, and optional local art paths are decoded without downloads.

## Evidence and outstanding acceptance

The AppId implementation follows [Steam ROM Manager's primary code](https://raw.githubusercontent.com/SteamGridDB/steam-rom-manager/master/src/lib/helpers/steam/generate-app-id.ts): reflected CRC32 of the UTF-8 stored quoted `Exe` followed by `AppName`, with bit 31 set. There is no terminating NUL. The launch identifier is `(uint64(appid) << 32) | 0x02000000`. Binary type layouts follow [ValvePython VDF's primary implementation](https://raw.githubusercontent.com/ValvePython/vdf/master/vdf/__init__.py). This corrects the older candidate in the design document; current Steam behavior is still an owner-PC acceptance gate.

Synthetic tests exercise VDF roundtrip/unknown fields, malformed inputs, AppId vectors, idempotent edits/collisions, approval/closed-Steam/stale-preview guards, backup retention/removal, art naming/transparency, fake runtime registry/env/library detection, stat changes, real synthetic child exit/log/state preservation and duplicate launch locks. These tests do not launch emulators, start SteamVR or access a real Steam library. Owner verification of one approved shortcut with art and the three flat games remains required. Headset acceptance is separately deferred by the owner.

Local Windows 11 / MSVC 2022 / Qt 6.8.3 Release verification on 2026-10-09: all four CTest targets passed in 39.01 seconds (smoke 0.73, catalog 1.27, install 31.12, launch/Steam 5.87). The launch/Steam executable reports 27 passing cases, zero failures/skips. Windows art tests use native system fonts without showing a window; Linux CI uses the offscreen platform. An independent reviewer also ran the synthetic suite successfully. Remote Linux/Windows CI and real owner-PC Steam/emulator acceptance remain separate gates.
