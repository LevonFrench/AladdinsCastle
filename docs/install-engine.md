# Install engine specification

Status: **research spec, 2026-10-08**. Not implemented. This defines how the Hub runs a game's `install.toml` variants, and the emulator and helper installs they depend on, so that every install is safe and repeatable.

Owner decisions already taken are cited by their D-number in [workshop.md](workshop.md). Choices made here are marked **PROPOSAL**. Choices only the owner can make are marked **OPEN** and collected in §18.

**Sources (repo-relative):** [game-packages.md](game-packages.md) §1-§5, [frontend.md](frontend.md) §3-§6, [ui/03-detail-and-install-flow.md](ui/03-detail-and-install-flow.md) §0-§3, [config-spec.md](config-spec.md) §2, §4, §8-§10, [game-schema.md](game-schema.md) (`[[media]]`), [legal.md](legal.md), [architecture.md](architecture.md), [libacvr-contract.md](libacvr-contract.md) (patch rules, list item 8 near line 223), [games/timecris/install.toml](../games/timecris/install.toml), [games/vcop2/install.toml](../games/vcop2/install.toml), and the PC-mode emulator matrix (kept in the hub wiki, not in this repo).

**Mod Hub references** use `Core/...` relative to the Mod Hub repository (MIT). A reference clone sits at `_refs/PCVR-Mods-Installer-Hub/`; it is gitignored, so the line numbers may not resolve on every checkout. They were read on 2026-10-08.

## 0. Decisions at a glance

| ID | Decision | Status |
|---|---|---|
| E1 | Recipes are data only. No recipe-supplied code. No `install.ps1` escape hatch in v1. | PROPOSAL |
| E2 | 13 step kinds plus an implicit `verify`. An unknown kind stops planning. `uninstall` is not a step kind. | PROPOSAL |
| E3 | Undo is generated by the engine for each step kind, from a write-ahead journal. A recipe cannot author undo. | PROPOSAL |
| E4 | The ownership manifest is the only authority for uninstall, repair and update cleanup. Hand-written remove lists are not allowed. | PROPOSAL |
| E5 | No expression language. Conditions use structured `when` tables; value mapping uses a declarative `map`. | PROPOSAL (rewrites one line of `games/timecris/install.toml`) |
| E6 | Downloads are HTTPS only, from allow-listed hosts, pinned to a tag and a SHA-256. No mirrors, no web archive, no fuzzy asset matching. Stricter than the Mod Hub. | PROPOSAL |
| E7 | Nothing is marked installed until verify passes. The state file is the last durable write of a commit. | Owner rule, ui/03 §0.7 |
| E8 | Never elevated. Registry writes, if any, are HKCU only. | PROPOSAL |
| E9 | Config writes touch managed keys only. Original comments, order, encoding and line endings survive. | PROPOSAL (from config-spec §8 layering and the Mod Hub INI helper) |
| E10 | Installs land in `installed/<game>/<variant>/`, built in a staging folder and swapped in. In-place variants are a named exception with backups. | PROPOSAL |
| E11 | Emulators and helpers the Hub installs live in one install-root folder, `emulators/<id>/`. | PROPOSAL, naming OPEN (§18.1) |
| E12 | Every line of output is one typed event. The console, the log file and the CLI are views of that stream. | PROPOSAL (ui/03 §3) |

## 1. Rules and terms

**Rules.** The engine enforces these, and tests cover each one.

- **R1.** Never fetch, bundle, link to or generate game content ([legal.md](legal.md)).
- **R2.** Nothing is marked installed before verify passes.
- **R3.** Remove only what the manifest records. Never remove user media, saves, profiles or anything under `user/`.
- **R4.** Every change outside staging is written to the journal before it happens.
- **R5.** No elevation, no UAC prompts, no changes to system or security settings (Defender, SmartScreen, SteamVR).
- **R6.** An unknown step kind, variable, host or key in a security-relevant table stops the run at planning, before any download.

**Terms.**

| Term | Meaning |
|---|---|
| Recipe | One `[variant.<id>]` block with its steps, in `games/<id>/install.toml`. |
| Variant | One VR setup for a game (for example a PCVR build, or a Quest build). |
| Step | One `[[variant.<id>.step]]` entry. |
| Artifact | A file the engine downloads (pinned) or the user locates. |
| Media | User-owned game material. Never downloaded. Declared with `[[media]]` in `game.toml`. |
| Tool | An emulator or helper (for example `adb`), installed by the Hub or located by the user. |
| Install root | The AladdinsCastle folder ([config-spec.md](config-spec.md) §2). |
| Install dir | `installed/<game>/<variant>/`, unless the variant is in-place (§10.4). |
| Run | One install, repair, update or uninstall invocation. It has an id and its own journal. |
| Plan | The expanded, resolved list of steps and artifacts for a run. Dry-run prints it. |
| Manifest | Per-variant ownership record (§9). |
| Journal | Per-run write-ahead log (§9.2). |
| Verify | The post-install check (§6.14). |

## 2. Components

One core library with no UI. The Hub, the CLI and the tests all drive it.

| Module | Job |
|---|---|
| Recipe loader and validator | Parses `install.toml`, checks the format version, step kinds, literal fields and host rules (§5.1). |
| Expander | Resolves `${...}` placeholders and `when` conditions (§5.2-§5.3). |
| Planner | Builds the plan and the dry-run text. No side effects. |
| Artifact store | Downloads, resumes, validates and caches artifacts (§8). |
| Step executors | One per step kind (§6). |
| File operation layer | Every write goes through it: journal, backup, atomic replace, ownership rows (§9). |
| Verifier | Post-install and light (existence) checks (§6.14). |
| State store | Checksummed state and manifest files, previous generation kept (§4). |
| Event bus | Emits typed events to console, log, CLI and UI (§12). |

CLI commands on the same core: `validate`, `explain` (as in [config-spec.md](config-spec.md) §8), `hash-check`, `plan` (dry run), `install`, `repair`, `update`, `uninstall`. The Python `tools/validate_catalog.py` checks the catalog today. The engine's `validate` becomes the source of truth for `install.toml` once it exists (§15.6).

## 3. Lifecycle

### 3.1 Persisted states

Each variant has a state file at `user/state/installs/<game>/<variant>.toml` (layout in §4). The `state` field is one of:

| State | Meaning | Written when |
|---|---|---|
| `not-installed` | No state file, or the state says so. | After an uninstall commit. |
| `installing` | A run is in progress. Found at startup means crash recovery (§3.6). | At run start. |
| `installed` | Verified. Manifest final. | Commit only. |
| `installed-with-warnings` | Verified, but the run kept user files or a shortcut failed. Shown amber. | Commit. |
| `installed-with-skipped` | Verified, but optional steps were skipped. Shown amber, never as plain "Installed" (ui/03 §2.9). | Commit. |
| `updating` | Staged swap in progress (§10.2). | At update start. |
| `repairing` | Repair run in progress. | At repair start. |
| `uninstalling` | Uninstall in progress. | At uninstall start. |
| `uninstall-incomplete` | Some manifest rows could not be removed. Manifest kept with those rows. | At uninstall end. |
| `failed` | Last run failed and was rolled back. Carries `previous_state`. | After rollback. |
| `rollback-incomplete` | Rollback could not finish. Journal kept. Blocks new runs for this variant until resolved. | Rollback failure. |

**Derived display states** are not stored. They come from the variant status, the preflight checks, the state and the update cache. They map to the game-packages §2 labels:

| Display state | Derived from | Precedence |
|---|---|---|
| Coming soon | `status = "planned"` in the recipe | 1 |
| Update available | installed, and the cache shows a newer version | 2 |
| Installed | `installed*` state and the light verify passes | 3 |
| Repair needed (new label, PROPOSAL) | `installed*` state, light verify fails | 4 |
| Needs your files | not installed; a required media is missing or unverified | 5 |
| Needs an emulator | not installed; a required tool is missing | 6 |
| Ready to install | not installed; all preflight checks green | 7 |
| Install failed, rolled back (PROPOSAL) | state `failed` | shown until next run |

This follows the precedence in ui/03 §0.3 (planned, update, installed, needs files, needs emulator, ready to install), with "repair needed" inserted.

### 3.2 Run phases (in memory)

Each phase is emitted as an event. None is persisted except through the journal and the state.

```
not-installed
   | Install (preflight green, variant not planned)
   v
planning ---------> downloading ----------> verifying-artifacts ----------> applying
   |                    |                         |                            |
   |                    |                         |                            v
   |                    |                         |                    verifying-install
   |                    |                         |                            |
   +--------------------+-------------------------+--------------+-------------+
                                                                |  pass            fail / cancel
                                                                v                    v
                                                           committing           rolling-back
                                                                |                  |     |
                                                                v                  v     v
                                                   installed (or -with-*)   failed   rollback-incomplete

installed --(update check: cache only, no install I/O)--> update-available
update-available --Update--> updating (staged, §10.2) --> verifying-install --> committing --> installed (new version)
                                                              fail --> rolling-back --> failed (old version still installed)
installed --Repair--> repairing --> verifying-install --> committing --> installed
installed --Uninstall (preview, confirmed, no running game)--> uninstalling --> not-installed
                                                                         \--> uninstall-incomplete
```

### 3.3 Transition rules

| From | Event | Guard | To | Writes |
|---|---|---|---|---|
| not-installed | Install | Preflight green; variant not `planned`; recipe valid | planning | Lock file, run header |
| planning | Plan built | No unknown step, variable or host; disk estimate fits | downloading, or applying if every artifact is cached | Journal header |
| downloading | Artifacts fetched | Every pin verified (§8.7) | verifying-artifacts | Artifact cache |
| verifying-artifacts | Checks pass | Archive inspection and content guard pass (§8.8-§8.9) | applying | None |
| applying | Steps done | Every non-skipped step done | verifying-install | Journal, manifest checkpoints, staging |
| verifying-install | Pass | Verify (§6.14) | committing | None |
| committing | Commit done | Manifest, journal commit, state all written | installed, -with-warnings, or -with-skipped | State |
| Any run phase | Step error or cancel | None | rolling-back | Journal |
| rolling-back | Undo complete | Every `done` op undone | failed (with `previous_state`) | State |
| rolling-back | Undo incomplete | Some op could not be undone | rollback-incomplete | State |
| installed | Repair | None | repairing | State |
| installed | Update | Staged tree verified | updating | State |
| installed | Uninstall | Preview accepted; no game process from install dir | uninstalling | State |
| uninstalling | All rows handled | None | not-installed | State removed |
| uninstalling | Some rows kept | Any row could not be removed | uninstall-incomplete | State, manifest |

### 3.4 Cancel

- **Allowed:** during planning, during a download (the `.part` file is kept, §8.6), and between steps. Cancel rolls back journalled work. The message is "Cancelled at step 3 of 5. Changes were rolled back."
- **Not allowed:** while a `run` child process or an `adb` operation is in progress. The engine waits for it to finish, or applies the `run` timeout rule (§6.13).

### 3.5 Concurrency and locks

- **One mutating run per install root at a time.** A global queue, not per-variant. Reason: shared tools and the shared `emulators/` folder. **PROPOSAL** (§18.12).
- Per-variant lock file `user/state/locks/<game>--<variant>.lock`, holding PID, process start time and run id. A lock is stale when its process is gone. Where the platform offers an OS file lock, prefer it (Qt's `QLockFile` is a candidate).
- Read-only operations (`validate`, `explain`, `plan`, light verify) take no lock.
- A variant in `installing`, `updating`, `repairing`, `uninstalling` or `rollback-incomplete` blocks other runs until resolved.
- Two variants of one game may not share an install dir. The validator checks this.

### 3.6 Crash and interruption recovery

On startup, scan `user/state/installs/**/*.journal.jsonl` for runs with no terminal record (a `commit` or a completed rollback).

1. Show: "An install of <game> / <variant> stopped at step 3 (applying). Nothing is marked installed. Roll back the partial work?" The default is **Roll back**, which is the safe choice. The alternative is **Retry from start**, which rolls back first and then runs the same plan again.
2. Rollback replays the journal backwards (§9.5). If the state says `updating`, restore the complete generation (§10.2).
3. **No automatic resume** of a half-finished run. Each step is idempotent on its own, but a run is not resumed mid-way (**PROPOSAL**).
4. **Special case:** a journal with a `commit` record but a state still at `installing` means the crash came after the manifest and journal commit. Finish the state write as `installed` (roll forward). Do not roll back.

## 4. Persisted files

`user/` is gitignored and never shipped ([config-spec.md](config-spec.md) §2).

```
user/state/installs/<game>/<variant>.toml             state file (checksummed, §4.2)
user/state/installs/<game>/<variant>.manifest.toml    ownership manifest (§9)
user/state/installs/<game>/<variant>.journal.jsonl    write-ahead journal, current or last run (§9.2)
user/state/located.toml                               located media and tool paths, with size, mtime, sha256
user/state/backups/<sha256>                           content-addressed pre-change copies (§9.3)
user/state/staging/<run>/                             extracted archives and fresh-install work, transient (§6.6)
user/state/preserve/<run>/                            user files moved aside during update (§10.3), transient
user/state/locks/<game>--<variant>.lock               run lock (§3.5)
user/cache/artifacts/<sha256>                         artifacts, content-addressed, kept for offline repair (§8.5)
user/cache/github.json                                release tags, ETags, rate-limit marks (§8.4)
user/cache/hashes.json                                hashes of located files, keyed by path, size and mtime
user/logs/<game>-<variant>-<UTC>.log                  console text (§12.3)
user/logs/<game>-<variant>-<UTC>.jsonl                machine-readable events (§12.3)

installed/<game>/<variant>/                           the install, built in staging then swapped (§10.2)
installed/<game>/<variant>.staging-<run>/             staging, transient
emulators/<id>/                                       tools the Hub installed (E11)
```

Paths inside state files are relative to the install root when they are inside it, and absolute otherwise (located media).

### 4.1 Atomic writes

Write to a temp file in the same folder, flush, then replace (Qt's `QSaveFile` is a candidate). Keep the previous generation as `<name>.previous`.

On read, if the checksum fails, use `.previous` and log a warning. If both fail, mark the variant "unknown, repair needed" and offer Repair. **Never** silently forget an install.

Mod Hub writes its state the same way: a temp file, then a replace, with `KeepPrevious` (`Core/Modules/HubState.ps1:418-442`). The Mod Hub's plain `Set-Content` in its cache writer is not atomic (`Core/Prefetch-Versions.ps1:56`); we do not copy that.

### 4.2 Checksum envelope and canonical form

```toml
schema   = 1
checksum = "sha256:<hex>"          # over the canonical JSON of [data]

[data]
game              = "timecris"
variant           = "dr89-pcvr"
state             = "installed"    # §3.1
installed_version = "v1.2.0"       # a concrete tag, never "latest" or "cached" (§8.2)
recipe_sha256     = "<hex>"
run               = "<run id>"
install_dir       = "installed/timecris/dr89-pcvr"
previous_state    = ""             # set when state is failed
last_error        = ""             # step id and error code when failed

[data.bindings.media.example-set]
path     = "<absolute path>"
sha256   = "<hex>"
verified = true
```

**Canonical JSON for the checksum (PROPOSAL).** UTF-8 with no BOM. LF newlines. Object keys sorted in byte order. Strings escape only `"`, `\` and control characters, written as `\uXXXX`. No HTML escaping. Integers in decimal. Booleans lowercase. No floats (use strings for fixed decimals). The checksum covers the canonical JSON of the parsed data, not the TOML text, so comments and whitespace do not break it.

The Mod Hub had to write its own canonical JSON because `ConvertTo-Json` escapes characters differently on Windows PowerShell 5.1 and PowerShell 7 (`Core/Modules/HubState.ps1:261-265`). Our spec defines the bytes, and golden test vectors pin them (§15.1), so the Qt build, the CLI and the tests always agree.

**Schema versions.** Each file has `schema`. Migrations go forward only. A file with a newer schema than the engine knows opens read-only and refuses writes. Never downgrade.

## 5. Recipes and expansion

### 5.1 File shape

```toml
format  = 1                       # install.toml format version (new field, §17)
default = "dr89-pcvr"

[variant.<id>]
title          = "..."
quality        = "true3d"         # true3d | theatre
status         = "stable"         # planned | wip | stable
upstream       = "https://..."    # display only
license        = "MIT"            # display only, shown in the plan
needs          = { media = ["<set key>"], tools = ["adb"], headset = "developer-mode" }
installed_when = "file:${install_dir}/Example.exe"   # §5.5
placement      = "install-dir"    # install-dir | in-place (§10.4)
preserve       = ["saves/**"]     # user files kept across update and repair (§10.3)
perf           = "SOLID"          # optional, ui/03 §2.15

[[variant.<id>.step]]             # ordered; see common keys below
id   = "zip"
do   = "github-release"
what = "Download the example build"
...

[variant.<id>.launch]
exe = "${install_dir}/Example.exe"
cwd = "${install_dir}"

[variant.<id>.uninstall]
keep = []                         # optional extra protection globs only. No "remove" key (E4).
```

**Common step keys:**

| Key | Meaning |
|---|---|
| `id` | Unique within the variant. Required when a later step refers to this step's outputs. |
| `do` | The step kind (§6). |
| `what` | Human label, used in the console header. |
| `optional` | Boolean, default `false`. A skipped optional step makes the result amber (§3.1). |
| `when` | Structured condition (§5.3). |
| `note` | Shown in the plan and the console. |

**Validation** (pack validator, runs in CI and at load):

- `format` is known.
- `do` is one of the 13 kinds, and `registry` is recognised but disabled in v1 (`E_STEP_DISABLED`, §18.3).
- Security-relevant fields are literal (§5.2).
- Every artifact step has a pinned tag or version and a 64-hex `sha256`.
- Hosts are a subset of the global allow-list (§8.1).
- Step ids are unique. Install dirs are unique per variant.
- No `[variant.<id>.uninstall]` `remove` key.
- No `latest` as an install target (§8.2).

The examples in `games/timecris/install.toml` and `games/vcop2/install.toml` need ids on their steps to pass. Today's `${upstream_dir}` becomes `${steps.<extract-id>.dir}`.

### 5.2 Expansion

**Syntax.** `${name}` or `${name.attr.attr}`. Segments are `[a-z0-9_-]+`. Environment reads use `${env:NAME}`. A literal `$${` is an escaped dollar-brace.

No nesting. Values are not re-expanded. No functions, no arithmetic.

**Namespaces.** Resolved at plan time. An unknown name is `E_EXPAND_UNKNOWN`.

| Name | Resolves to | Available from |
|---|---|---|
| `install_root` | The AladdinsCastle folder | Always |
| `install_dir` | `installed/<game>/<variant>/`, or the in-place root | Always |
| `download_dir` | `user/cache/artifacts/` | Always |
| `staging_dir` | `user/state/staging/<run>/` | Applying phase only |
| `emulators_dir` | `emulators/` | Always |
| `game.id`, `game.title` | From `game.toml` | Always |
| `media.<key>.path`, `.dir`, `.name`, `.sha256`, `.verified` | Located user media | After `locate-package` or `require-media` |
| `tools.<id>.path`, `.dir`, `.version` | Tool installed by the Hub or located by the user | After the tool is ready |
| `steps.<id>.path`, `.dir`, `.sha256`, `.bytes`, `.tag` | Output of an earlier step | After that step |
| `settings.<k>` | Per-game settings (cover, laser, gun angle) | Per game |
| `profile.<k>` | Per-player profile (handedness, height) | Per player |
| `env:NAME` | Environment variable | Path fields only, and only for names in the allow-list |
| `platform` | `windows-x64`, `linux-x64` or `quest-android` | Always |

The allow-list for `env:` is `LOCALAPPDATA`, `APPDATA` (read as a path only), `USERPROFILE`, `ProgramFiles`, `ProgramFiles(x86)`, `XDG_DATA_HOME` and `HOME`.

**Retired names.** `${setup_dir}` ([config-spec.md](config-spec.md) §4) and `${game_dir}` ([config-spec.md](config-spec.md) §2) become `install_dir` and `media.<key>.dir`. `${upstream_dir}` (used in `games/timecris/install.toml`) becomes a step output (§17).

**Literal fields.** These are never expanded: `url`, `repo`, `tag`, `asset`, `sha256`, `package`, `hosts`. The download target can be read as plain text in review. `env:` is not allowed in URLs, `args` or config values.

### 5.3 Conditions (`when`)

Structured tables only. No operators beyond these.

```toml
when = { setting = "settings.laser", equals = true }
when = { media = "example-set", state = "verified" }
when = { tool = "adb", state = "present" }
when = { all = [ { ... }, { ... } ] }      # also: any = [...], not = { ... }
```

These cover the two conditional uses in the current examples. They replace `${settings.cover == 'duck' ? 1 : 0}` in `games/timecris/install.toml` (line 43). The `map` form that replaces the rest of that expression is in §6.8 (E5).

### 5.4 Path rules

After expansion, every path must pass:

1. Separators are normalised. NUL is rejected. `..` segments are rejected after normalisation. Drive-relative paths (`C:foo`) are rejected. UNC is rejected in v1.
2. The result is under an allowed root: `install_root`, `emulators_dir`, `download_dir`, `staging_dir`, or the declared in-place root or located media folder for `copy-media` and in-place variants.
3. The parent's real path (after symlinks and junctions) passes rule 2 again.
4. Windows-only names are rejected on every platform, so one recipe behaves the same everywhere. These are reserved device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9, with or without an extension), names containing `:`, and names ending in a dot or a space.
5. Case: Windows is case-insensitive and Linux is not. The engine records the on-disk name it created. Two names that differ only by case inside one run are an error.

### 5.5 `installed_when` predicates

| Form | Meaning |
|---|---|
| `file:<path>` (a bare path means this) | The path exists and is a file. |
| `file:<path>` with `sha256 = "..."` (table form) | Exists, and its hash matches. Existence alone is the default. |
| `adb:package:<id>` | The package is installed on the selected headset (state `device`). |
| `version:<exe path>` with `>= "<x.y.z>"` | The file's version is at least this. |

The Mod Hub checks file presence only (`Core/Modules/DetailView.Page.ps1:3030-3033`, ui/03 §1.21 item 3). Here `installed_when` is one input to verify, never the whole check (§6.14).

## 6. Step kinds

### 6.0 Summary

| Kind | Key inputs | Outputs | Dry-run | Idempotent when | Undo record |
|---|---|---|---|---|---|
| `github-release` | `repo`, `tag`, `asset`, `sha256`, `to` | `path`, `sha256`, `bytes`, `tag` | Prints the pin and the URL host. Optional HEAD. | Cache file matches the pin | Cache only, nothing to undo |
| `download` | `url`, `sha256`, `name`, `to`, `alt_urls` | `path`, `sha256`, `bytes` | Prints the URL host and the pin | Cache matches the pin | Cache only |
| `locate-package` | `pattern`, `kind`, `sha256` (optional) | `path`, `sha256`, `bytes`, `verified` | Searches, lists candidates | Located entry matches | Located entry removed |
| `require-media` | `media`, `verify` | `media.<key>.*` | Read-only check | Same path, size and mtime | None (read-only) |
| `copy-media` | `media`, `to`, `mode` | `path`, `mode_used` | Prints mode and space | Target is the same file, or same hash | Remove the link name, or our copy |
| `extract` | `from`, `to`, `strip`, `include`, `exclude` | `dir`, `files` | Inspects the archive, lists the plan | Same archive and recipe give the same rows | Per-file rows (§9.5) |
| `copy` | `from`, `to`, `include`, `exclude` | `dir`, `files` | Lists the plan | Same hashes | Per-file rows |
| `write-config` | `file`, `format`, `set` | Managed keys | Diff of managed keys only | Key already holds the after-value | Prior value, or removal |
| `patch-text` | `file`, `edits`, `base_sha256` | `patched` (edit ids) | Count check per edit | All markers present | Backup restore |
| `registry` (disabled in v1) | `key`, `value`, `type` | None | Read-only | Value equals | Prior value, or delete if ours |
| `adb-install` | `apk`, `package`, `device`, `replace` | `package`, `version_code` | Prints the adb commands | Same version code | `adb uninstall` (fresh installs only) |
| `shortcut` | `targets`, `name`, `exe`, `args` | `paths`, `steam_entry` | Prints paths and targets | Same target already present | Remove if the target is ours |
| `run` | `exe`, `args`, `cwd`, `sha256`, `wait` | `exit_code`, `log` | Prints the full command | Not by default | None, unless the recipe declares `undo` (§18.4) |
| `verify` (implicit) | `installed_when`, manifest | pass, warn or fail | None | Not applicable | Not applicable |

Undo records are written to the journal and copied into the manifest (§9.1). They are never authored by the recipe, except for the `run` case in §18.4.

### 6.1 `github-release`

- **Inputs:** `repo` (owner/name, literal), `tag` (pinned, literal), `asset` (an exact name, or a glob that must match exactly one asset on that release), `sha256` (required), `bytes` (optional), `to` (default `download_dir`).
- **Resolution:** the URL is built from the pinned fields, `https://github.com/<repo>/releases/download/<tag>/<asset>`. No API call is needed to download. The API is used only to confirm the asset exists (optional, cached) and to read GitHub's asset digest when one is offered. A digest is a cross-check. It never replaces the pinned hash.
- **Output:** the content-addressed path, plus `sha256`, `bytes`, `tag` and `url`.
- **Idempotency:** if `download_dir/<sha256>` exists and hashes to the pin, skip the download ("[OK] Already downloaded, SHA-256 verified").
- **Failure modes:**
  - Tag 404: `E_RELEASE_NOT_FOUND`. "The pinned release no longer exists. Install a newer recipe version." The engine never picks another release.
  - Asset missing or matched twice: `E_ASSET_AMBIGUOUS`.
  - Hash mismatch: `E_HASH_MISMATCH`. The file is deleted. One retry is allowed, then the manual drop-in.
  - Rate limit: `E_RATE_LIMITED` (§8.4).
  - Redirect to an unlisted host: `E_HOST_NOT_ALLOWED`.

### 6.2 `download`

- **Inputs:** `url` (HTTPS, literal), `sha256`, `bytes` (recommended), `name`, `to`, `alt_urls` (optional, default none, §8.3), `max_bytes` (default from global config).
- **Output and idempotency:** as `github-release`.
- **Types:** a non-HTML payload that arrives as `text/html` is treated as a login or error page: `E_FORMAT`.

### 6.3 `locate-package`

- **Inputs:** `what`, `pattern` (filename glob), `kind` (`archive`, `file` or `folder`), `sha256` (optional), `search` (optional extra folders; default Downloads).
- **Behaviour:** read-only search, with no writes and no network. The engine lists candidates with name, size, mtime and hash result. The user confirms one. Nothing is used silently (frontend.md §4).
- **Partial downloads** are excluded by suffix: `.crdownload`, `.part`, `.tmp`, `.opdownload` (`Core/Modules/InstallerFoundation.ps1:131`).
- **Dropped paths** are canonicalised the same way as the Mod Hub: quotes removed, bare drive `D:` becomes `<local-root>/` (`Core/Modules/InstallerRecovery.ps1:11-30`).
- **Verified state:** with `sha256`, the candidate must match. Without it, the state is "found, not verified" (ui/03 §2.5).
- **Output:** `path`, `sha256`, `bytes`, `verified`. Stored in `located.toml`.
- **Failure modes:** not found gives `E_MEDIA_MISSING` (action: "Find my files"). A candidate that fails validation is rejected, and the original is not touched.
- **Content guard:** an upstream package that bundles game content is rejected (§8.9).

### 6.4 `require-media`

- **Inputs:** `media` (a key from `[[media]]`), `verify` (`hash`, `name` or `none`; default `hash`), `set` (the set name, used to pick expected hashes).
- **Behaviour:** checks the user's located media. Never copies (that is `copy-media`). Hashing large files runs in a worker, with progress. Results are cached in `user/cache/hashes.json` by path, size and mtime.
- **Output:** `media.<key>.path`, `.dir`, `.name`, `.sha256`, `.verified`, plus `match` (`exact`, `name` or `none`).
- **Failure modes:** `E_MEDIA_MISMATCH`. Text: "This file is not the set this setup needs. It matches <other> or nothing known." The file is kept, and the user is asked for a different one. Never replaced.
- **Expected-hash format** is OPEN (config-spec §10, §18.7).

### 6.5 `copy-media`

- **Inputs:** `media`, `to` (inside the install dir), `mode` (`link`, `copy` or `auto`; default `auto`).
- **Behaviour in `auto`:** a hard link when the source and target are on the same volume. FAT and exFAT have no hard links, so copy there. Windows symbolic links need Developer Mode or elevation, so the engine never creates them. If linking fails and a copy would need a second full-size file, ask first (`E_LINK_UNSUPPORTED`).
- **Output:** `path`, `mode_used`.
- **Idempotency:** the target is the same file (same file id for a link), or has the same hash for a copy. The console says "[OK] Already in place (linked)".
- **Ownership:** recorded with origin `user-media-link` or `user-media-copy`. Uninstall never deletes media. A link name is removed only when its file id matches the user's file, so the data survives. A copy is removed only if the engine created it and its hash still matches the record.
- **Failure modes:** target exists with different content: `E_WRITE_CONFLICT`. Refuse. Never overwrite.
- **Dry-run:** prints the mode and the disk needed.

### 6.6 `extract`

- **Inputs:** `from` (step id or path), `to` (default `install_dir`), `strip` (leading folders to remove; `auto` removes one wrapper folder shared by all entries), `include` and `exclude` (globs), `max_entries` (default 50 000), `max_expanded` (default 4 times the archive size, with a 20 GB ceiling), `overwrite` (default `keep-user-edited`).
- **Behaviour:** inspect the archive first (§8.8). Extract into `staging_dir/extract/`. Then the file operation layer merges the files into `to`, one at a time. Each file is journalled, backed up if it existed and is not ours, and recorded in the manifest.
- **Overwrite rules:** a file is `config` if its extension is `ini`, `cfg`, `json`, `toml`, `yaml`, `xml`, `txt` or `csv`, and `binary` otherwise. See §9.4 for how each class is handled when the user has edited it. This matches the ui/03 §2.8 sample ("kept your copies").
- **Output:** `dir`, `files` (count), and the list of rows.
- **Idempotency:** the same archive hash and the same recipe give the same rows. Files that already match are no-ops.
- **Failure modes:** `E_ARCHIVE_UNSAFE`, `E_ARCHIVE_LIMITS`, `E_ARCHIVE_ENCRYPTED`, `E_ARCHIVE_CORRUPT` (§8.8). Staging is removed, and nothing is partly extracted. `E_DISK_SPACE`. `E_FILE_IN_USE` (a file is open by a running process; ask the user to close the game). `E_WRITE_DENIED`.
- **Dry-run:** inspects the archive (no writes) and prints counts, collisions, and the kept or replaced plan.

### 6.7 `copy`

- **Inputs:** `from` (a step output, or a path under `games/<id>/setup/` or a pack folder), `to`, `include`, `exclude`.
- **Behaviour:** the same merge as `extract`, without archive inspection.
- **Restriction:** `from` must not be a media path or a user folder (use `copy-media`). Checked at planning (`E_SOURCE_OUT_OF_SCOPE`).
- **Use:** our own shipped files, for example `setup/controls.toml` ([config-spec.md](config-spec.md) §5).

### 6.8 `write-config`

- **Inputs:** `file`, `format` (`ini`, `cfg`, `toml`, `json` or `yaml`; `xml` is in §18.2), `create` (default `false`; create the file only if it is true), and `set`, an array of managed-key entries:

```toml
[[variant.<id>.step]]
id     = "cfg"
do     = "write-config"
file   = "${install_dir}/quest-options.cfg"
format = "cfg"                              # key=value lines, no sections
set = [
  { key = "physical_crouch", from = "settings.cover",      map = { hold_to_shoot = 0, hold_to_cover = 0, toggle = 0 }, default = 0 },
  { key = "laser_enabled",   from = "settings.laser",      bool = { on = 1, off = 0 } },
  { key = "gun_pitch",       from = "settings.gun_pitch",  type = "int" },
  { key = "left_handed",     from = "profile.left_handed", bool = { on = 1, off = 0 } },
]
```

- **Entry forms:** a literal (`{ key, value }`), a typed read (`{ key, from, type }`), a `map` (`{ key, from, map, default }`), or a boolean map (`{ key, from, bool = { on, off } }`).
- **ini sections:** for `format = "ini"`, each entry also names its section, `section = "config"`. The key is the literal key inside that section (Flycast's `vr.Laser` is one key, not a path).
- **Types:** `string`, `int`, `float` (with `decimals = n`), `bool` (style per file: `01`, `truefalse` or `yesno`) and `path`.

**Merge rules (E9).**

- Only keys listed in `set` are touched. Every other line, key, comment, blank line, section order and value stays exactly as it was.
- **ini and cfg:** line-based edit. A key is replaced in place, keeping its spacing style. A missing key is appended to its section, and a missing section is created at the end. A duplicate key in the target section is refused (`E_AMBIGUOUS_KEY`).
- **toml, json and yaml:** parse with a round-trip-capable parser where one exists. Otherwise re-serialise and warn `[!!] Comments were not preserved in <file>`. Keys use dotted paths. Array elements are not supported in v1.
- **Encoding:** detect the BOM (UTF-8, UTF-16LE). Keep the file's encoding and its line endings (CRLF or LF). New files are UTF-8. Never convert silently.
- **Atomic:** temp file in the same folder, then a replace. The original is backed up first (§9.3).
- **Record:** for each key, `prior` (absent or a value) and `after` (the value written). Undo restores `prior` only if the current value still equals `after`. Otherwise keep the user's value and warn.

**Output:** the managed keys written.

**Dry-run:** a diff of managed keys only, plus warnings such as "comments will be lost."

**Failure modes:** `E_CONFIG_PARSE` (with line and column; the original is untouched), `E_WRITE_DENIED`, `E_AMBIGUOUS_KEY`.

**Re-run mode:** the settings save in ui/03 §2.10 runs only `write-config`, and only for keys whose `from` changed. No reinstall.

### 6.9 `patch-text`

- **Inputs:** `file` (a file the install owns, or one that has been backed up. Never a user media file), `edits` (`[{ id, old, new, count, marker }]`), and `base_sha256` (the hash of the file before patching, required when the file is upstream).
- **Behaviour (libacvr-contract.md, around line 223):** exact fragments only, with no fuzzy match. The number of occurrences of `old` must equal `count`. `marker` is inserted by the patch, so a later run can prove the edit is present.
- **Idempotency:** if every `new` and marker is present and no `old` remains, the result is "already applied". A mixed state is `E_PATCH_DRIFT`, and nothing is written.
- **Undo:** a whole-file backup is taken before the first edit. Undo checks that the current hash equals the post-patch hash. If it does not, the user's version is kept and the user is warned.
- **Failure modes:** `E_PATCH_DRIFT` (upstream changed, so the recipe needs updating), `E_PATCH_COUNT`.
- **Dry-run:** prints each edit with its count check.

### 6.10 `registry` (disabled in v1)

- **If enabled:** HKCU only. Key prefixes are allow-listed in engine code, for example `HKCU\Software\AladdinsCastle\`. Writes to HKLM are refused (E8).
- **Behaviour:** read the previous value and its type (or record its absence), write, journal. Undo restores the prior value, or deletes the value only if we created it and it still equals ours.
- **Failure modes:** access denied is `E_REGISTRY_DENIED`. Never an elevation prompt.
- **Detection:** the engine does not read the registry to find games in v1. Linux has no registry (§14).
- **Current status:** no recipe uses it. Dropping it is recommended (§18.3). While disabled, a recipe that uses it gets `E_STEP_DISABLED` at planning.

### 6.11 `adb-install`

- **Inputs:** `apk` (step output or located artifact), `package` (the expected application id, literal), `device` (optional serial; default is the only device in state `device`), `replace` (`update` or `fresh`; default `update`).
- **Preconditions:** the `adb` tool is present (`needs.tools`). The device is in state `device`.
  - `unauthorized`: prompt "Accept the prompt in the headset", with a Check again button.
  - `offline`: reconnect guidance.
  - No device: "Connect the headset" (USB, Link or Air Link).
- **Identity check before any write:** read the package name from the APK's `AndroidManifest.xml` (an APK is a zip, read through the safe reader in §8.8). A mismatch with `package` is `E_PACKAGE_MISMATCH`.
- **Dry-run:** prints the commands, for example `adb -s <serial> install -r <apk>`. Reads `pm list packages` and the previous version from `dumpsys package`. Writes nothing to the device.
- **Output:** `package`, `version_code`, `previous_version_code` (0 for a fresh install).
- **Verify:** `pm list packages` contains the package, and `dumpsys` reports the expected version code.
- **Idempotency:** package present with the expected version code: skip with "[OK]".
- **Failure mapping** (the names are the strings adb and PackageManager print, to be checked against the platform-tools version the tool recipe pins):

| adb or pm message | Our code | Recovery |
|---|---|---|
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | `E_DEVICE_STORAGE` | Free storage on the headset. |
| `INSTALL_FAILED_VERSION_DOWNGRADE` | `E_ADB_REFUSED` | Offer uninstall first. That deletes app data on the headset, so it needs explicit consent. |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` (signature differs) | `E_ADB_REFUSED` | Same consent path as downgrade. |
| `INSTALL_PARSE_FAILED_NO_CERTIFICATES` | `E_PACKAGE_UNSIGNED` | Refuse. |
| Anything else | `E_ADB_REFUSED` | Full adb output in the log. |

- **Undo:** a fresh install is undone with `adb uninstall <package>`, which deletes the app's data on the headset. This is shown in the uninstall preview and needs confirmation. An upgrade has no undo, because the previous APK is not kept on the headset. The run says so, and the state reflects the new version.

### 6.12 `shortcut`

- **Inputs:** `targets` (`desktop`, `start-menu` or `steam`), `name`, `exe`, `args`, `cwd`, `icon` (optional, inside the install dir).
- **Desktop and start menu:** a `.lnk` on Windows, or a `.desktop` file on Linux (§14). Created only if absent. Never overwrite a shortcut that points somewhere else. On a name clash, add a suffix and tell the user.
- **Steam:** adds a non-Steam shortcut by writing the user's `shortcuts.vdf` (binary VDF). Steam must be closed, because a running Steam overwrites the file on exit. If Steam is running, prompt: "Close Steam to add the library shortcut, or skip it." Skipping is allowed only for optional steps. Otherwise it is a warning. Back up the file first, and record the entry so it can be removed later. This format is undocumented and needs a round-trip test before it ships (§18.9).
- **Output:** `paths`, `steam_entry`.
- **Failure modes:** "could not create" is a `[!!]` warning, not a failure. The Mod Hub treats a failed shortcut the same way (ui/03 §2.8). A VDF parse error is `E_STEAM_FILE`: skip with a warning, and leave the original untouched.
- **Undo:** remove only shortcuts we created whose target still points into our install dir (ui/03 §2.12 step 4). A Steam entry is removed only if its exe is still ours.
- **Dry-run:** prints the shortcut paths and targets.

### 6.13 `run`

- **Inputs:** `exe` (inside the install dir, or a tool path from `tools.<id>.path`), `args` (a list of strings, each expanded), `cwd`, `sha256` (required for scripts, and for any exe that did not come from a pinned artifact), `what`, `note`, `wait` (default `true`), `timeout` (default 30 minutes), `expect_exit` (default 0).
- **Rules:**
  - Scripts (`.ps1`, `.bat`, `.cmd`, `.py`, `.sh`) need `sha256`.
  - The engine never changes execution policy and never passes bypass flags. A recipe that needs a bypass is refused. Ship a tool instead.
  - System interpreters (`powershell`, `cmd`) are reachable only through the engine's own system-tool list, and only with a pinned script hash (§18.4). `games/timecris/install.toml` uses `${tools.powershell}` in its Quest variant, so this rule decides that example.
  - Elevation is never requested. A child that asks for it fails.
- **Before starting:** show the full command line, `cwd`, the environment variable names (not values), and the script's hash. The confirmation is a labelled button (for example "Run Install-ROM.ps1"), not the Enter key. The Enter-to-continue rule in ui/03 §3 is for ordinary prompts, not for running code.
- **Dry-run:** prints the same, and does not execute.
- **Output:** `exit_code`, `log` (stdout and stderr to a file, with env values redacted).
- **Idempotency:** none by default. A step that is not idempotent is marked `idempotent = false`, and a Repair that would re-run it is refused with a message to run a full install.
- **Journal:** records what started and how it exited. It is not undone automatically. The uninstall preview lists it: "External program ran: <what>. Not reversed automatically."
- **Failure modes:** non-zero exit is `E_RUN_EXIT`, with the log attached. Timeout is `E_RUN_TIMEOUT`, and the user chooses: keep waiting, or stop the child process the engine started. The engine never stops the game or any other process.

### 6.14 `verify` (implicit, last step of every run)

Checks, in order:

1. `installed_when` is true (§5.5).
2. Every manifest row exists. Owned binaries match their `sha256`. Config rows have their managed keys at the after-value, or are marked user-edited (warn).
3. Required shortcuts exist.
4. Tool versions meet the minimum.
5. For `adb` variants: package present and version code as expected.

**Result:** `pass`, `pass-with-warnings` or `fail`. A fail triggers rollback and state `failed`. Pass with warnings gives `installed-with-warnings`. Skipped optional steps give `installed-with-skipped`.

**Survival check.** After placing files, wait 3 seconds and re-check every manifest file. The Mod Hub does this because antivirus tools quarantine files (`Core/Modules/InstallerSafety.ps1:4123`). A missing file is `E_FILE_REMOVED`. Show the active antivirus name if one is known, and the exclusion steps (§13). The engine never adds an exclusion.

**Commit order (E7),** modelled on `Complete-PCVRInstallTransaction` (`Core/Modules/InstallerFoundation.ps1:230-326`):

1. Write the final manifest (atomic).
2. Append the `commit` record to the journal and flush it.
3. Write the state file as `installed` (atomic, previous generation kept).
4. Delete staging.
5. Emit `done`.

If steps 1 to 3 fail, restore the previous bytes of every file written, then roll back. The state file is written last, so it is the only durable statement that the variant is installed. The §3.6 roll-forward rule covers a crash between steps 2 and 3.

## 7. Dry-run and plan

- `plan` is the same planner as `install`. Its output is the same text that `install` will act on. Golden tests check this (§15.3).
- **Three levels:**
  - `plan`: reads the recipe and the state. Nothing else.
  - `preflight`: adds filesystem reads, hashing of located media, and the adb device list.
  - `resolve`: adds network metadata calls (release HEAD, cached API reads), rate-limited and cached (§8.4).
  - `install` runs `resolve` and then applies. `--dry-run` runs up to `resolve` and writes only to cache and logs.
- **Checked at plan, so they fail before any download:** unknown step, variable or host; a missing tool (shown as a flag); missing media (a flag); a target that is not writable (probe, §13); disk space (planned sizes times 1.5, plus a backup estimate); path rules; archive listings for archives already on disk.
- The plan gives the step count `t` for the `--- [n/t] ---` headers, after `when` filtering. Optional steps are counted.

**Worked example (expanded plan for the PCVR variant in `games/timecris/install.toml`, illustrative):**

```
PLAN  timecris / dr89-pcvr   format 1   installs as: install-dir   license: MIT (port code)
  needs     media: <set key>   tools: none   headset: none
  1/4  Find the VR build        locate-package  pattern TimeCrisisVR-*-windows-x64*.zip   (no download)
  2/4  Extract                  extract -> installed/timecris/dr89-pcvr/   inspect: ok, no link entries
  3/4  Set up your files        copy-media -> installed/timecris/dr89-pcvr/roms/   mode auto (hard link)
  4/4  Write settings           write-config quest-options.cfg (4 managed keys)
       Create shortcut          shortcut steam -> installed/timecris/dr89-pcvr/Play SteamVR.cmd
  verify  installed/timecris/dr89-pcvr/TimeCrisisVR.exe
  disk    estimate ok on target
```

The upstream package in this example must be a content-free build. The build the upstream release ships with game files is rejected by the content guard (§8.9), as `games/timecris/install.toml` already says.

## 8. Download and artifact safety

### 8.1 Transport

- **HTTPS only.** Any `http:` URL is a plan error. TLS verification is always on. TLS 1.2 is the minimum (the Mod Hub sets Tls12, `Core/Modules/InstallerSafety.ps1:507`).
- **Global allow-list** (shipped in engine config, changed by repo PR only): `github.com`, the storage host that release-asset redirects land on (verify and record at implementation), `api.github.com`, and the official hosts of tools declared in `data/emulators/` (for example a project's own site). No ROM, ISO, BIOS or media hosts. CI reviews the list.
- **Per-recipe hosts** must be a subset of the global list. The validator checks this.
- **Redirects:** at most 5 hops. Each hop's host is checked against the allow-list, and the scheme must stay HTTPS. Use Qt's manual redirect policy, or the equivalent, so each hop is checked. The Mod Hub follows redirects automatically (`Core/Modules/InstallerSafety.ps1:512`), which this rule tightens.
- **User-Agent:** `AladdinsCastle-Hub/<version>`. No cookies. No credentials, and no tokens in v1.
- **Timeouts:** connect 30 s, read stall 120 s (the Mod Hub's values, `Core/Modules/InstallerSafety.ps1:513-514`).

### 8.2 Pins and versions

- **Every artifact has a pinned tag or version and a SHA-256.** The recipe's hash is the trust root. A checksum from the release page, or a GitHub asset digest, is a cross-check that must agree. It never replaces the pin.
- **`latest` is never an install target.** A tool with `version = "latest"` (the example in [frontend.md](frontend.md) §4) becomes an offer: "Newer version available (not tested with this setup): vX. Install side by side?" Installing it creates a new pinned entry only after the user chooses it. This changes the frontend example (§17). **PROPOSAL**.
- **Installed version must be a concrete tag.** The Mod Hub rejects labels such as "latest" and "cached" (`Core/Modules/InstallerSafety.ps1:2959`). The same rule holds here.
- **Pins are checked at `resolve`.** A pinned tag that is gone is `E_RELEASE_NOT_FOUND`. The engine never falls back to "latest", or to a release with a similar name. The Mod Hub's fallback to any release with a same-leading-word asset (`Core/Modules/InstallerSafety.ps1:3248-3350`) is not copied.
- **Release filters by name are not used.** The Mod Hub drops tags containing "source", "hub-patch", "sdk" or "symbols" (`Core/Prefetch-Versions.ps1:92`). Here a release counts as matching only if it contains the pinned asset name exactly once.
- **Tools without a verified official pin stay locate-or-search only** until their pin is researched. The matrix lists Dolphin, Model 2 Emulator, Yaba Sanshiro and the TeknoParrot main UI this way.
- **Licence gate.** For a tool, the official download is a user-side fetch and the Hub never redistributes it. Show the licence in the plan. The matrix flags DuckStation (CC BY-NC-ND 4.0) and gives no clear open licence for Redream and TeknoParrot. For those, an automatic install is opt-in per tool until licence review is done.

### 8.3 Source ladder

1. The pinned primary URL.
2. Pinned `alt_urls` in the recipe. Only on official hosts of the same project, and only with the same SHA-256. Default: none (§18.10).
3. Manual drop-in. The engine opens the official page after the user presses Enter. The user downloads the file and drops it in. It is then validated exactly as a download (§8.7).

**Not in the ladder (E6):**

- `web.archive.org` or any other archive or mirror. The Mod Hub routes pinned GitHub assets there when a hash is set (`Core/Modules/InstallerSafety.ps1:620-625`). That contradicts frontend.md §4 ("Never a mirror"), so it is not copied.
- Third-party mirrors.
- GitHub API fuzzy asset search.
- Discord-hosted files. The Mod Hub's Discord flow (`Core/Modules/InstallerFoundation.ps1:139-215`) is not in v1.
- DepotDownloader and Steam depots (`Core/Modules/InstallerSafety.ps1:2448-2668`). They fetch game content.

### 8.4 GitHub access and rate limits

- **Downloads need no API.** The URL is built from repo, tag and asset name.
- **"Is there a newer release?"** uses the releases redirect: a HEAD to `https://github.com/<repo>/releases/latest`, reading the final tag. The Mod Hub's prefetch does this on purpose, to avoid the 60-per-hour unauthenticated API limit (`Core/Prefetch-Versions.ps1:60-62`). The redirect is not a documented API. If it changes, fall back to the API and log it.
- **API calls** (asset digests, release lists) send `If-None-Match` with the cached ETag. GitHub's REST documentation says a 304 response does not count against the primary limit. Verify at implementation.
- **On 403 or 429:** read `retry-after` or `x-ratelimit-reset`. Store `rate_limited_until` for the host in the cache. Show "GitHub is rate-limiting this computer until HH:MM. Using last known versions." No retry loops. Cached values stay usable.
- **Circuit breaker:** after the first network failure in one scan, no more network checks in that scan (`Core/Modules/Filter.ScanSources.ps1:1201`). A scan-wide deadline also applies (`Core/Modules/Filter.ScanSources.ps1:1623`).

### 8.5 Cache

- `user/cache/github.json` holds `{ "owner/repo": { tag, checked (UTC, ISO 8601), etag, rate_limited_until } }`. Tags have a 6-hour TTL, as in the Mod Hub (`Core/Prefetch-Versions.ps1:32`). A stale value is kept if the network fails.
- Writes are atomic (§4.1).
- The cache is never inside the program folder (ui/03 §1.17).
- **Artifact cache** (`user/cache/artifacts/<sha256>`) is content-addressed. An artifact is kept while an installed variant references it, so Repair works offline. Otherwise it is evicted least-recently-used, to a size limit (default 10 GB, configurable). Never evicted while a run uses it.

### 8.6 Resumable downloads

- Stream to `<name>.part` in 128 KB chunks. Progress every 250 ms as "X MB of Y MB (pct%) - rate MB/s" (the Mod Hub's format, `Core/Modules/InstallerSafety.ps1:505-557`).
- **Resume** with HTTP `Range` and `If-Range` set to the stored ETag or Last-Modified. If the server answers 200 instead of 206, or the validator has changed, restart from zero.
- A `.part` survives a network failure or a cancel. It is deleted on hash mismatch.
- **Promotion:** after the size, SHA-256 and type checks (§8.7), rename to `download_dir/<sha256>`. The rename is on the same volume and is atomic. The name is the hash, so a wrong file cannot pass as the artifact.
- **Space:** check free space before starting (size times 1.5, plus staging).
- **Size cap:** the recipe's `max_bytes`, with an 8 GiB global ceiling. Exceeding it aborts with `E_ARTIFACT_TOO_LARGE`.

### 8.7 Validation before a file may replace anything

In this order:

1. Size, if declared.
2. SHA-256 against the pin. Always.
3. Type by magic bytes for the declared kind: zip `PK 03 04`, 7z `37 7A BC AF 27 1C`, exe `MZ`, gzip `1F 8B`, tar by header, MSI `D0 CF 11 E0`. Compare with the Mod Hub's `Test-DownloadedPayload` (`Core/Modules/InstallerSafety.ps1:381-453`).
4. Reject HTML and login pages for non-HTML kinds, by content (`<!doctype html`, `<html`).
5. Archive inspection (§8.8).
6. Content guard (§8.9).
7. The recipe's expected entries, if the recipe lists any. Compare with the Mod Hub's anchor patterns (`Core/Modules/InstallerSafety.ps1:454-476`).

Only then does the file get its content-addressed name.

### 8.8 Archive safety (zip, 7z and tar)

Inspection runs before any extraction, for every archive type. The Mod Hub inspects zip only. For 7z it reports "uninspectable" and relies on the extractor (`Core/Modules/InstallerSafety.ps1:839-870`). Not copied.

- **Paths:** reject absolute, drive-qualified and UNC entries. Reject `..` after normalisation, and any entry that resolves outside the destination.
- **Names:** reject reserved Windows device names (§5.4), names containing `:` (alternate data streams), names ending in a dot or space, and names that differ only by case from another entry in the same archive. These checks run on Linux too, so one archive behaves the same everywhere.
- **Links:** reject symbolic links, hard links, device nodes and FIFOs. A zip symlink shows up as Unix mode `0120000` in the external attributes.
- **Limits:** `max_entries` (50 000); `max_expanded` total (default 4 times the archive size, 20 GB ceiling); a per-entry compression ratio (1000:1 for entries over 1 MB) as a zip bomb guard. The Mod Hub computes `ExpandedBytes` and never limits it (`Core/Modules/InstallerSafety.ps1:849`).
- **Encrypted entries:** refuse (`E_ARCHIVE_ENCRYPTED`).
- **Extract only into `staging_dir`**, never straight into an install folder. The file layer merges afterwards (§9).
- **Corrupt archive** (CRC failure mid-stream): `E_ARCHIVE_CORRUPT`. Staging is removed, and the artifact is evicted and re-downloaded once.
- **Library:** libarchive (BSD-2-Clause) is the candidate for zip, 7z and tar (§18.6). The Mod Hub bundles 7-Zip (`Core/Modules/InstallerSafety.ps1:1376`). That needs licence notes, and it does not give the inspection API we need. RAR is not supported (`E_FORMAT`).

### 8.9 Never game content: enforcement

Four layers:

1. **Host allow-list** (§8.1) has no content hosts.
2. **Step shape.** `download` and `github-release` cannot name a media key, so a recipe cannot request a romset ([legal.md](legal.md)). Media is used only by `locate-package`, `require-media`, `copy-media` and `run` arguments.
3. **Content guard** on every archive and file the engine takes in. It rejects entries whose names match a content list (media set file names, disc image extensions such as `.chd`, `.iso`, and `.bin` with `.cue` pairs, BIOS file names), or whose hashes match a content-hash list. The result is `E_CONTENT_GUARD`, and nothing is written. The list lives in `data/content-guard.toml` (format OPEN, §18.11). The list itself must hold names and hashes only, never content.
4. **Artifact kinds.** The artifact record holds `kind` (`tool`, `upstream-build`, `config`). There is no `content` kind.

The repo `.gitignore` already excludes `*.zip`, `*.7z`, `*.chd`, `*.iso`, `*.bin`, `*.cue` and `*.apk` (`/user/`, `/installed/` and `/emulators/` too). That blocks accidental commits. The guard is the runtime check.

## 9. Ownership manifest

### 9.1 Schema

`user/state/installs/<game>/<variant>.manifest.toml`, checksummed like the state file:

```toml
schema        = 1
checksum      = "sha256:<hex>"
game          = "timecris"
variant       = "dr89-pcvr"
run           = "<run id that last changed this manifest>"
recipe_sha256 = "<hex>"
install_dir   = "installed/timecris/dr89-pcvr"     # or an absolute in-place root

[[file]]
path          = "TimeCrisisVR.exe"                  # relative to install_dir (or in-place root)
kind          = "binary"                             # binary | config | data
origin        = "extracted"                          # extracted | copied | written | patched | linked | user-media-link | user-media-copy | adopted
step          = "extract"
sha256        = "<hex>"                              # the hash we wrote (the "after")
bytes         = 0
prior         = "absent"                             # absent | backup
prior_sha256  = ""                                   # when prior = backup
backup        = ""                                   # backup id (sha256) in user/state/backups
user_edited   = false
owners        = ["dr89-pcvr"]                        # shared ownership (§9.6)

[[config]]
file        = "quest-options.cfg"
key         = "physical_crouch"
prior       = "absent"                               # absent | value
prior_value = ""
after_value = "1"

[[shortcut]]
path         = "<absolute path>"
kind         = "desktop"                             # desktop | start-menu | steam
target       = "<absolute path>"
steam_entry  = ""                                    # when kind = steam

[[run]]
step         = "external"
what         = "<label>"
exit_code    = 0
reversible   = false
undo         = ""

[[adb]]
package             = "<application id>"
version_code_after  = 0
previous_version_code = 0                            # 0 = fresh install
undo                = "adb-uninstall"                # or "none"
```

This replaces the Mod Hub's CSV (`Core/Modules/OwnedModFiles.ps1`), and the `.ownership.csv` name in ui/03 §2.12 (§17).

### 9.2 Write rules

- **Journal first.** Before any change outside staging, append an `intent` record that holds the planned after-state and any backup id, then flush. Then make the change, then append `done`. On startup, intents without `done` are reconciled against the disk (§3.6).
- **Checkpoint the manifest after every step,** not only at the end. The Mod Hub writes its CSV after the copy loop (`Core/Modules/OwnedModFiles.ps1:135-137`). A mid-copy error throws before that point (line 74 and the surrounding loop), which leaves copied files that nothing records.
- **The manifest is the authority** for what we own. The journal is for crash recovery only. After commit, keep the journal for 30 days or the last 20 runs, for diagnostics, and then compact it.

### 9.3 Backups

- Before any change to a file that exists and is not already ours, or to a user-edited config, copy its bytes to `user/state/backups/<sha256>`. Content addressing means identical bytes are stored once. Backups are referenced by manifests, and are never deleted while a manifest refers to them. Never stored inside the install dir.

### 9.4 Changing a file we own

| Current state of an owned file | `binary` | `config` |
|---|---|---|
| Hash equals the recorded `sha256` | Replace (update path) | Replace (update path) |
| Hash differs (user edited) | **Fail closed**, `E_FILE_CHANGED`. Offer "Replace (your version is backed up)" as an explicit choice. Never automatic. | **Keep the user's version.** Warn "[!!] Kept your edited <file>". Mark `user_edited = true`. Keep the recorded `after` so uninstall keeps the file too. |

The Mod Hub refuses to overwrite a changed file (`Core/Modules/OwnedModFiles.ps1:72-74`). Keeping edited configs and failing closed on binaries follows ui/03 §2.12 ("Files the user edited are kept, and the panel says so").

A file that is not owned and already exists is backed up, then replaced, and recorded with `prior = "backup"`.

### 9.5 Uninstall

1. **Preview, no writes.** Counts per kind. The list of kept user files and user-edited files. External actions that cannot be reversed (`run`, and `adb` with app data). What is never touched: media, saves, profiles, `user/`, the base game. Buttons: **Remove** and **Cancel**. Cancel changes nothing (ui/03 §1.11).
2. **Pre-check.** A game process running from the install dir means: ask the user to close it. Do not kill it (ui/03 §2.12 step 7). An open file means `E_FILE_IN_USE`, naming the file.
3. **Reverse the journal** for this manifest, in reverse order:
   - **file** (origin `extracted`, `copied`, `written` or `patched`) whose hash still equals `sha256`: delete. If `prior = backup`, restore the backup and verify its hash.
   - **file** whose hash differs: keep it, and list it as "kept: edited by you". Never delete a changed file.
   - **config** keys: restore `prior_value` only if the current value equals `after_value`. Otherwise keep and warn.
   - **shortcut**: remove if its target is still in our install dir.
   - **linked media:** remove the link name only if its file id matches the user's file.
   - **copied media:** delete only if we made the copy and its hash matches the record.
   - **run:** not reversed. Listed.
   - **adb:** `adb uninstall` for fresh installs, after confirmation.
4. **Directories** we created: remove only if empty, deepest first. Never recursively delete a directory we did not create.
5. **State:** remove it, giving `not-installed`. If any row could not be removed, keep the manifest with just those rows, and set `uninstall-incomplete`. Never drop rows silently.
6. **Never delete:** user media, `user/` (state, cache, logs), any `preserve` path, the base game, and anything not in the manifest.

**Quest.** Uninstall with `adb uninstall <package>`, after an explicit choice to keep or delete the app's data on the headset (ui/03 §2.12 step 6).

### 9.6 Shared ownership

Two variants of one game may share a file only if the recipe says both produce it byte-identically. The validator checks that the pins match. Ownership is then `owners = [...]`, and uninstall removes a shared file only when its last owner goes. A shared loader installed outside our tools (BepInEx-style) is never in our manifest (ui/03 §1.19).

### 9.7 Adoption (opt-in)

The Mod Hub can adopt a file that already exists and is byte-identical to its payload (`Core/Modules/OwnedModFiles.ps1:83-93`). Here, adoption happens only during Repair, with consent, and records `origin = "adopted"`. The default is backup, then replace.

### 9.8 Repair

- Compare manifest rows with disk. Light check: existence. Full check: hash.
- A missing owned file is restored from the artifact cache. Only if the artifact is gone is the pin downloaded again.
- A changed owned binary: offer a replace (§9.4). A changed config: keep it, and show the diff.
- Extra files in the install dir are not touched.
- Repair is the install steps re-run for the rows that differ, followed by verify.

## 10. Update, reinstall and repair

### 10.1 Update detection

- **From the cache only** (§8.5). For pinned variants: the recipe's `version` is newer than the installed version (concrete tags only). For upstream releases: the cache shows a newer tag that no recipe pins yet. That gives a "newer upstream, not tested" offer (§8.2).
- **Text:** "Update available: v1.3.0 (you have v1.2.0)" (ui/03 §2.12).
- Never silent. Never run on app start without the user asking for a check.

### 10.2 Staged swap

1. **Stage.** Install the new version into `installed/<game>/<variant>.staging-<run>/`, on the same volume, with all steps and journal entries. The live tree is untouched.
2. **Verify the staging tree.** `installed_when` is applied to the staging path, and the manifest rows are checked.
3. **Swap** with two renames on the same volume: `<variant>` becomes `<variant>.previous-<old version>`, then `<variant>.staging-<run>` becomes `<variant>`. If the second rename fails, rename the first back.
4. **Verify the live tree** again. Commit (§6.14 order): new manifest, journal commit, state `installed` with the new version.
5. **Keep `.previous-<old>`** until the new version has passed verify and the user has launched it once, or for 7 days, whichever comes first (**PROPOSAL**, §18.13). Then delete it, using the old manifest's rules (§9.5).
6. **Failure before step 4:** swap back if the swap happened. Keep the failed staging folder as `failed-<run>` for the log. The state stays on the old version. The message: "Update to v1.3.0 failed. v1.2.0 is still in place."

The update needs roughly twice the variant's size on disk, and the plan checks that.

### 10.3 Preserved user files

- Recipe `preserve` globs (saves, profiles, per-game overrides the user wrote). Before staging, the live copies are moved aside to `user/state/preserve/<run>/`, then restored into the new tree, then verified. This is the Mod Hub's `Protect-InstallUserData` and `Restore-InstallUserData` (`Core/Modules/InstallerSafety.ps1:2893-2953`).
- A leftover preserve folder from an interrupted update is restored first, before anything else. It is never overwritten (`Core/Modules/InstallerSafety.ps1:2922-2927`).
- If the restore fails, the preserve folder is kept, and the state says so.

### 10.4 In-place variants (named exception)

Some setups must sit beside the user's game files. `games/vcop2/install.toml` says the mod files go next to the game's own executable. Declare `placement = "in-place"` and `in_place_root = "${media.<key>.dir}"`.

- Still journalled and manifest-owned, so uninstall works the same way.
- A staged swap is not possible inside the game folder. Update = back up every file the update will overwrite (§9.3), write the new files, verify. Rollback = restore the backups in reverse. This is weaker than the staged swap, so the UI says: "Update in the game folder. Rollback restores the previous files."
- Preflight checks that the game folder is writable without elevation (§13). Protected system folders are refused.
- The vcop2 note "No game files are modified on disk" is only true for the original game files. The recipe adds files, and it may overwrite a config. The text should say "adds files to your game folder. Originals are backed up." (§17.)
- Whether in-place variants stay in v1 is OPEN (§18.5).

### 10.5 Reinstall and repair

- **Reinstall** is an install run with the existing manifest as its baseline. If the version is the same, it is an in-place repair pass (§9.8). If the version differs, it is an update (§10.2).
- **Repair** is §9.8. It needs no network unless an artifact is missing from the cache.

## 11. Failures, recovery and error codes

### 11.1 Recovery panel

Based on ui/03 §2.9 and `Core/Modules/InstallerRecovery.ps1:97-184`. No Exit button, as in the Mod Hub.

- **Heading:** "INSTALL STOPPED AT STEP n OF t. Nothing was marked installed."
- **Actions:** Retry this step · Retry from start · Open log · Open install folder · Open Downloads · Clear handover.
- **Drop zone.** A dropped file, folder or path is a handover. It is stored in the run context object, not in an environment variable. The Mod Hub stores it in `PCVR_HUB_RECOVERY_INPUT` (`Core/Modules/InstallerRecovery.ps1:33-42`), which is process-global state we do not want. It is canonicalised (§6.3), validated by the step's own validator (§8.7), and then used by the next retry.
- **Rollback** is offered when partial work exists and the run is not committed. The default for a failed run is rollback before retry. "Retry this step" keeps completed steps, and is allowed only when the journal shows them consistent.

## 12. Logging and the console

### 12.1 Event stream

Each line of output is an event: `{ts, run, kind, step?, index?, total?, text, code?, path?}`. Kinds: `plan`, `step` (header), `ok`, `warn`, `fail`, `work`, `detail`, `prompt`, `verify`, `done`.

The console, the log file and the CLI are renderers of this one stream (E12, ui/03 §3). Nothing keeps a second copy of the text.

### 12.2 Grammar

The text form. Colours are the ui/03 §2.7 tokens.

```
============================================================
  <Game title> - <Variant title>
  AladdinsCastle installer
============================================================

--- [1/4] Find the VR build ---
 [OK] <file> found in <folder>
 [!!] <warning. The step continues.>
 [..] <work in progress>
 [XX] <failure. The step stops. The recovery panel opens.>
      <detail lines, indented two spaces>
 >>> <prompt>
```

- **Header rule:** 60 `=` characters.
- **Step header:** `--- [n/t] Title ---`. `t` is the number of steps that will run after `when` filtering. Optional steps are counted.
- **Markers:** exactly `[OK]`, `[!!]`, `[XX]` and `[..]`. Prompts start `>>>`.
- **Final line**, one of exactly these: "Installed", "Installed, with 1 warning", "Installed, with skipped steps", "Install stopped at step n of t. Nothing was marked installed.", or "Rolled back."

The final lines are fixed text, so the run can never print "complete" after a failed check. That is the Alba failure in ui/03 §1.14.

### 12.3 Log files

- `user/logs/<game>-<variant>-<YYYYMMDD-HHMMSS>Z.log`, in UTC, with the same text as the console. A `.jsonl` file beside it holds the events. Each line is written and flushed as it happens, so a crash keeps everything up to the failure.
- **Retention:** the last 50 runs or 200 MB, oldest first.
- **Diagnostics export** ([frontend.md](frontend.md) §1) zips the logs and state. It uploads nothing.
- **Redaction:** paths are kept, since they are local. Environment values and token-like strings are never logged. `run` output goes to its own file, which the log refers to.

**CLI exit codes:** 0 installed (any verified state). 1 failed and rolled back. 2 rollback incomplete, or repair needed. 3 cancelled and rolled back. 4 nothing to do. 64 bad usage.

## 13. Elevation, antivirus and SmartScreen

- **No elevation.** The engine never requests admin, never runs a child elevated, and never writes HKLM. The Mod Hub runs some installers with `RequiresAdmin` (ui/03 §1.6). That is not copied.
- **Writability probe** before any write: create and delete a probe file in the target folder (`Core/Modules/InstallerSafety.ps1:1664`). A failure gives `E_WRITE_DENIED`: "This folder is not writable by your account. Choose a folder you own." A common cause is Program Files. A Steam library under Program Files is a typical example.
- **Settings are never changed.** Defender, SmartScreen and SteamVR settings included. The Mod Hub's antivirus exclusion flow shows steps (`Core/Modules/InstallerSafety.ps1:3985-4043`). We show steps too, and never add an exclusion.
- **Mark of the Web.** The engine does not remove `Zone.Identifier` streams and does not run `Unblock-File`. Files from GitHub carry the mark, so an unsigned binary may trigger SmartScreen on first launch. Say so in each game's README troubleshooting section ([game-packages.md](game-packages.md) §5).
- **Survival check** after placing files (§6.14). Show the active antivirus name when it is known. The Mod Hub reads SecurityCenter2 and filters by the real-time bit (`Core/Modules/InstallerSafety.ps1:3937-3978`). Show the compact notice from `Get-AntivirusNoticeLines` (`Core/Modules/InstallerSafety.ps1:3892-3935`).
- **Our own binaries** will be unsigned at first. Code signing is OPEN and outside this spec.

## 14. Linux and Steam Frame

D21 ranks Steam Frame first, streamed from a PC through SteamVR, then standalone on SteamOS. In v1 the Hub runs on the PC and the Steam Frame plays through SteamVR. The differences below matter for the standalone step, and for any Linux-hosted parts.

| Topic | Windows (v1) | Linux and SteamOS (later) |
|---|---|---|
| Install root default | Portable folder | `$XDG_DATA_HOME/aladdinscastle`, or the portable folder if a portable marker exists. SteamOS: `/home` only, since the root filesystem is read-only. |
| Windows-only binaries | Yes | Run only where the recipe declares a Linux artifact. A Windows-only recipe reports "Windows only" at plan. Proton and Wine are out of scope. |
| Case | Insensitive | Sensitive. Match on locate, record the on-disk case. Collisions are refused on both OSes. |
| Archive names | Windows rules | Windows name checks run on Linux too (§8.8). |
| Executables | `.exe` | `chmod +x` only where the archive mode says so. Never setuid, never chown. |
| Shortcuts | `.lnk` | `~/.local/share/applications/*.desktop` |
| Steam shortcuts | `shortcuts.vdf` in Steam userdata | `~/.local/share/Steam/userdata/<id>/config/shortcuts.vdf`. Flatpak Steam keeps its files under `~/.var/app/com.valvesoftware.Steam/` (verify). Steam must be closed, as on Windows. |
| Registry | HKCU, if enabled | None. The step is unavailable. |
| Files in use | Windows locks open executables | No mandatory lock. Check `/proc` for processes holding the files. |
| Atomic rename | Replace-rename | `rename(2)`. The two-rename directory swap works on one filesystem. |
| Hard links | NTFS yes. FAT and exFAT no. | ext4, btrfs and xfs yes. vfat and exFAT no. |
| Symbolic links | Not created (privilege) | Not created in v1, for parity. |
| AppImage | Not applicable | The mount is read-only. Never write into it. State and installs go under XDG paths. |
| Flatpak | Not applicable | The sandbox limits file access, so the install root needs a portal or an explicit filesystem permission. Deferred. |
| adb | Pinned platform-tools zip | The same pinned zip. Quest on Linux needs udev rules. |
| Line endings | Keep the file's own | Same |
| Paths | Drive letters. UNC refused. | `/`-rooted. `~` is never expanded in recipes. |
| Elevation | None | None. No `sudo`. No writes under `/usr`. |

## 15. Test plan

### 15.1 Unit tests (no network; temp directories only)

- **Expander:** names and escapes, unknown names, the env allow-list, rejection of templated literal fields, the path rules (drive-relative, UNC, `..`, reserved names, `:`, trailing dot or space, case collisions).
- **Conditions:** truth tables for `when`.
- **Archive inspection:** a corpus of zip, 7z and tar archives with absolute paths, drive-qualified paths, `..`, symlink mode, hard links, reserved names, alternate data streams, case collisions, encrypted entries, a compression-ratio bomb, too many entries, bad CRCs, and truncation. Generated at test time. `.gitignore` excludes `*.zip` and `*.7z`, so fixtures are built by the test, or the owner allows an exception (§18.16).
- **Hash and type validators:** wrong hash, right hash with wrong magic, an HTML page with the right size, a surviving `.part` file.
- **write-config:** managed keys only. Comments, blank lines, order, BOM and CRLF preserved. Duplicate-key refusal. A missing section is appended. Re-serialisation warning. `prior` and `after` recorded. Undo only when the value equals `after`.
- **patch-text:** exact counts, drift, already applied, mixed state.
- **State checksum:** golden vectors (canonical JSON bytes to hash). Previous-generation recovery. A newer schema opens read-only.
- **Manifest:** uninstall returns the tree to its pre-install state, for random initial trees (property test). A user-edited binary fails closed. A user-edited config is kept. Shared ownership.
- **Journal crash injection:** inject a fault after each intent, after each write, after each `done`, during the manifest write and during the state write. Startup reconciliation must yield a complete rollback or a complete commit, with the tree exactly matching. The pass condition: no untracked file we created, and no manifest row without a file or a backup.

### 15.2 Integration tests with fakes

- **Fake GitHub:** an in-process HTTPS server with a test CA trusted only in the test profile. Routes: `/repos/o/r/releases/tags/<tag>` (200 JSON and 404), `/o/r/releases/latest` (redirect), `/o/r/releases/download/<tag>/<asset>` (redirects to a storage path on a second host, which checks each hop), 403 with `x-ratelimit-reset`, 429 with `retry-after`, a 200 HTML error page, a truncated body, Range and If-Range, ETag and 304, and a read stall to exercise the timeout.
- **Host guard:** a resolver that refuses any host outside the test allow-list. The engine must make zero connections elsewhere.
- **Fake adb:** a scripted binary answering `devices`, `install` (success, and each failure string in §6.11), `pm list packages` and `dumpsys package`. Plus a fake headset state machine: device, unauthorized, offline.
- **Fake tools:** a small test executable that prints and exits 0 or 1. It is generated by the test, not a real emulator.
- **Fixture game** at `tests/fixtures/games/example-game/`. Synthetic media, generated at test time, with its hashes computed. A synthetic upstream archive holding a dummy `example.exe` (a text file). A `settings.ini` with comments. An `install.toml` covering: `github-release`, `download`, `locate-package`, `require-media`, `copy-media` (link, and the copy fallback on a FAT-style temp volume), `extract` with wrapper strip, `copy`, `write-config` (ini and cfg), `patch-text`, `shortcut` (desktop, and Steam against a fake VDF), `run` (fake exe), `adb-install`, `verify`, uninstall, a v1 to v2 staged update, and an in-place variant.
- **Scenarios:** happy path. Warning path (a kept user config). Hash mismatch, then drop-in. Unknown step kind (plan stops, nothing downloaded). Verify failure, then rollback. Cancel between steps. Rate limit, served from cache. Update failure, with the old version kept. Uninstall with a user-edited binary. Repair after a deleted file.

### 15.3 Golden files

- Dry-run plan text for every `games/*/install.toml` and every fixture. Paths are replaced by `<INSTALL_ROOT>`, `<MEDIA>` and `<DOWNLOADS>`, and separators are normalised to `/`.
- Console transcripts for the scenarios in §15.2.
- Manifest and state files, with checksum fields recomputed and timestamps replaced.
- Golden updates are deliberate (an `--update-golden` flag), and reviewed in the PR.

### 15.4 Platform matrix

- Windows 10 and 11 on NTFS. Path with spaces and a drive letter. Read-only folder. Long path (over 260 characters, with prefix). Unicode names.
- exFAT or FAT temp volume for the `copy-media` fallback (manual).
- Linux ext4, for case collisions and mode bits (phase 2).
- A locked file (Windows exclusive open) gives `E_FILE_IN_USE`.

### 15.5 Upstream smoke (opt-in, scheduled, not CI)

- For each pinned release: check the release still exists, and that the asset still matches its SHA-256 (download, hash, discard). Reports drift. Covers tool and upstream-build recipes only, involves no game content, and respects §8.4.

### 15.6 Recipe lint (CI)

- `validate` over all games. Checks: format, step kinds, literal fields, hosts within the allow-list, pins present, no `latest` install target, no `remove` list, unique step ids, resolvable expansions, unique install dirs, `installed_when` inside the install dir or the declared in-place root, and no content names in archive lists.
- This extends the pattern of `tools/validate_catalog.py` from the catalog to `install.toml`. The Python checker is interim, and the engine's `validate` becomes the source of truth.

## 17. Drift in the existing docs

These contradictions were found while writing this spec. Each one needs a fix in the named doc.

1. **Tool folder name.** [frontend.md](frontend.md) §4 says `emulators/<id>/`. [game-packages.md](game-packages.md) §1 and ui/03 §2.5 say `tools/<id>/`. The repo's `tools/` is the dev CLI, and [architecture.md](architecture.md) uses it that way. Resolved in E11, pending §18.1.
2. **Manifest name and format.** ui/03 §2.12 names `installed/<game>/<variant>/.ownership.csv`. This spec uses a TOML manifest in user state (§9.1).
3. **Uninstall declarations.** [game-packages.md](game-packages.md) §1 has `[uninstall]` steps. [frontend.md](frontend.md) §3 has `uninstall` steps. `games/vcop2/install.toml` has `remove = [...]`. The manifest replaces all three (E4). `uninstall` is not a step kind.
4. **Step kinds.** [frontend.md](frontend.md) §3 lists 14, including `uninstall`. ui/03 §2.8 omits `copy`, `require-media`, `patch-text` and `registry`. This spec has 13, plus `verify`.
5. **Install format.** [game-packages.md](game-packages.md) §4 shows an inline `steps = [...]` array. `games/timecris/install.toml` uses `[[variant.<id>.step]]` tables, which ui/03 §2.16 item 2 already chose. Fix game-packages §4.
6. **Variable names.** `${setup_dir}` ([config-spec.md](config-spec.md) §4), `${game_dir}` (config-spec §2), `${upstream_dir}` (`games/timecris/install.toml`, undefined), `${download_dir}` ([frontend.md](frontend.md) §3), `${install_dir}` (install.toml). This spec uses `install_dir`, `download_dir`, `media.<key>` and `steps.<id>`.
7. **Expression syntax.** `games/timecris/install.toml` line 43 uses a ternary and `==`. Neither appears in [config-spec.md](config-spec.md) §2 or anywhere else. Replaced by `map` (E5).
8. **`version = "latest"`.** The tool example in [frontend.md](frontend.md) §4 contradicts the pinned rule in [frontend.md](frontend.md) §3 and [game-packages.md](game-packages.md) §1. Now an offer (§8.2).
9. **In-place vcop2 install.** `games/vcop2/install.toml` extracts into the user's game folder (`${media.vcop2-pc.dir}`). That conflicts with the `installed/` model in game-packages §1 and ui/03 §2.8, and with its own note "No game files are modified on disk." Now the named exception (§10.4). The note needs rewording.
10. **Hub technology status.** ui/03 line 5 says D4 is "still open". [workshop.md](workshop.md) D4 and [frontend.md](frontend.md) §6 say decided (Qt 6 / QML). Update ui/03.
11. **Folder names.** [architecture.md](architecture.md) lists `recipes/` and `setups/`. [game-packages.md](game-packages.md) puts `install.toml` in each game folder, and [config-spec.md](config-spec.md) §2 lists `setups/<setup-id>.toml`. This spec assumes `install.toml` lives in the game folder.

The tool manifest shape in §5.5 and §8.1 is what the engine needs. ## 18. Open decisions for the owner

1. **Tool folder name.** `emulators/<id>/` for everything the Hub installs (recommended), or `tools/<id>/`, which collides with the repo's dev `tools/`.
2. **Expression language.** Structured `when` and `map` only (recommended, rewrites one line of `games/timecris/install.toml`). Or a small grammar with a ternary. Also: is `xml` needed as a `write-config` format in v1?
3. **`registry` step.** Drop it from v1 (recommended; no recipe uses it). Or keep it, HKCU only.
4. **`run` with system interpreters.** Forbid by default and ship a tool instead (recommended), or allow `powershell` and `cmd` with pinned script hashes. The Quest variant in `games/timecris/install.toml` depends on this answer. Also: may a recipe declare an `undo` for `run`?
5. **In-place variants.** Keep them in v1 with weaker rollback (§10.4), or move the install to `installed/` with a documented launcher. The vcop2 setup is the test case.
6. **Archive backend.** libarchive (BSD-2-Clause, candidate) or the bundled 7-Zip the Mod Hub uses. 7-Zip needs licence notes, and does not give the inspection API we need.
7. **Expected-hash data for media** ([config-spec.md](config-spec.md) §10). MAME software-list XML (needs a licence check, and is data, not content), or our own `hashpack`.
8. **Skipping optional steps.** Allow it, with an amber "installed with skipped steps" result (PROPOSAL, as ui/03 §2.17 item 1).
9. **Steam shortcut in v1.** It needs a binary VDF writer, a Steam-closed rule and a round-trip test. In v1, or after the first Windows release?
10. **Alternate download URLs.** None by default (recommended). Or allow official-host alternates with the same SHA-256.
11. **Content guard.** Names only, or names and hashes. And who maintains the list. It must hold names and hashes, never content.
12. **Concurrency.** One mutating run at a time across the install root (recommended), or one per variant.
13. **Keeping the previous version** after an update: 7 days, or until the user launches the new one (§10.2).
14. **Latest tool releases.** An offer only (recommended), or an automatic update channel for emulators.
15. **Antivirus.** The wording of the compact notice, and whether the engine reads Defender's real-time state, as the Mod Hub does.
16. **Test fixtures.** Generate archives at test time (recommended), or allow `tests/fixtures/**/*.zip` through `.gitignore`.
17. **Linux.** Which standalone surface ships first: a SteamOS AppImage or a Flatpak. This spec defers Flatpak.
18. **Quest.** Should the engine check APK identity from the manifest before install (recommended)? Should uninstall keep the headset's app data by default?
