# DolphinXR gun drawing between game frames

Source design against DolphinXR commit `85c4266b29eb308d173fefa0f21f5cb77df3516a`. This is a placement and synchronization plan, not an implemented renderer or a headset result.

The pinned frame thread waits for a game publication in lazy mode, or wakes every display period in eager mode. After `WaitFrame()` and `BeginFrame()`, it consumes a new publication when one exists, otherwise keeps `last_frame`. It builds layers from those saved views immediately before `EndFrameDetached()`. No gun geometry is redrawn in that path. Relevant upstream source: `Source/Core/VideoCommon/VR/OpenXRManager.cpp`, lines 1246–1386. Its `XRPacing` fresh/repeat counters describe publications, not unique game simulation or geometry frames.

The insertion point for a new per-refresh gun pass is after the frame-thread content handoff settles and before the layer stack is passed to `EndFrameDetached()`. The pass must use the current `predictedDisplayTime` for both eye and controller pose lookup and must run on repeated-content cycles as well as fresh-content cycles. Lazy mode's publication wait prevents a guaranteed per-refresh pass; a mode that draws this pass must schedule every refresh. Simply enabling `EagerHeartbeat` resubmits old images and does not implement that pass.

Use a dedicated gun swapchain and a separate projection layer initially. Acquire and wait its images for this refresh, clear its own transparent colour and depth, draw both guns from the newest valid poses, release those images, then append its projection layer after the unchanged game layer. Preserve the game layer's original image and pose stamp: replacing its pose with a new pose would make the compositor reproject stale game pixels incorrectly. A separate layer fixes pose cadence but cannot provide correct occlusion against game geometry by itself. It is only a prototype until shared/reprojected game depth or a full per-refresh compositing path is implemented and verified. Do not advertise it as the depth-correct final gun.

The current D3D11 eye wrapper has no depth attachment (`Source/Core/VideoBackends/D3D/D3DOpenXR.cpp`, lines 195–197). Its `AcquireEyeFramebuffer()` and `ReleaseEyeTexture()` belong to the game's video-thread image ownership, and `SubmitFrame()` publishes the pose stamped with the presented XFB (lines 250–350). Never draw into a released front image or overwrite a swapchain the compositor may still read. The refresh pass needs its own backend-owned resources, context/queue synchronization, and explicit lifetime handling; it cannot call the existing OpenGL gun renderer against a D3D11 framebuffer.

The frame thread must not share mutable `m_eye_views` or the input subsystem's measured-now pose snapshots with the video thread. Add a dedicated predicted-pose snapshot for this pass. Restrict graphics queue locking to the actual commands and submit boundary, without holding the publication mutex while waiting for an image or GPU work. The existing queue lock inside `EndFrameDetached()` only guards submission and is not sufficient to make new D3D calls safe. Session loss, invisible sessions, controller loss and shutdown must end the frame protocol and release acquired images exactly once. Untracked hands suppress their gun draw without suppressing the other hand or the game.

Required evidence before acceptance: instrument game publications, distinct content, XR cycles and gun redraws separately; hold the game at 30 while confirming fresh gun poses at the selected display rate; check both eye projections, alpha edges, depth behavior, handedness, predicted-pose timing and missed-frame recovery. Then perform the physical-headset held-gun aiming and comfort checks. The frame-rate lane may establish that a particular game reaches the target rate, but a presentation counter alone cannot remove this requirement.
